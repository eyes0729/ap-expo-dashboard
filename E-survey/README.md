# AP 展会互动 · 问卷 + 转盘（手机 H5）

> 手机打开：`http://<局域网IP>:8099/E-survey/`（大屏左下角的二维码就指向这里）
> 本机预览：`http://localhost:8099/E-survey/`
> 管理面板：地址后加 `?admin=1`　·　重新参与一次：加 `?again=1`

逻辑照《AP展会互动问卷抽奖SOP》v2（2026-08-18）实现。

## 流程

```
扫码 → 开场（说明有抽奖，但不列奖品）→ 问卷（身份分流 2~3 题，逐题手动前进）
     → 转盘（四个奖品在这里才亮出来）→ 中奖页（可截图 / 可回显）
```

## 题目与分支

| 分支 | 题量 | 题目 |
|---|---|---|
| **所有人** | Q1 | 您的身份是？ A 跨境电商卖家/品牌商家 · B 供应商 · C 服务商 |
| **A 商家** | 共 4 题 | Q2 是否在用 Shopify 独立站（**参与判定**）· Q3 店铺月 GMV（仅落库）· Q4 微信/手机号（**必填**） |
| **B 供应商** | 共 3 题 | Q2 主营品类 · Q3 微信/手机号（**必填**） |
| **C 服务商** | 共 3 题 | Q2 公司规模（仅落库）· Q3 微信/手机号（**选填**） |

## 两条交互规则（这一版改的）

### 一、开场不列奖品

原先开场页把四个奖品逐条列出来。**问题是奖项不是抽的，是按答案判定的** ——
「免费 3 个 AP 来源订单」只发给答了「是，正在运营 Shopify」的商家。
先让人看见奖品再答题，等于把答案的方向写在题面上：没有店的人也会去选「正在运营」，
拿回来的线索就是脏的，而这份线索正是做这个问卷的唯一目的。

现在开场页只说「有抽奖、100% 中奖、约 30 秒」，配一条 答题 → 转盘 → 领奖 的流程条。
**四个奖品在转盘页完整展示**，那时答案已经提交、改不了 —— 所以这是延后展示，不是删掉。
验收里两头都断言了（首屏看不到 + 转盘页四格齐），只断言一头的话，
把奖品从产品里整个删掉也会「通过」。

### 二、选中不自动跳题

原先是选完 180ms 自动进下一题（省一次点击）。**代价是手滑点错当场就被带走**，
而且整个流程没有一个「我确认了」的动作。现在：

- 选中只更新选中态和进度条，**必须点「下一题」才前进**
- 必答题没答时「下一题」是**禁用**的 —— 比让人点下去再弹「请选一项」更早给出信号
- 选填题（服务商的联系方式）空着也能走，禁用规则只管必填题
- 键盘 Enter 与触屏走同一套规则：按钮是灰的时候 Enter 也不生效

顺带修掉一个由此暴露出来的真缺陷：**回头改身份时，上一条分支的答案不会再跟着落库**。
先选「商家」答完 Shopify / GMV，再退回改成「服务商」，旧版会把那两个字段
一起写进记录 —— 一条服务商线索上挂着店铺 GMV。自动翻页时代很难走到这条路径，
改成手动翻页后回头改身份变得很常见，所以必须处理（`clearBranchAnswers()`，
联系方式三条分支通用，予以保留不用重填）。

## 奖项判定（SOP 第三节）

| 身份 | 条件 | 奖项 | 盘面格 |
|---|---|---|---|
| 商家 | Q2 = 是，正在运营 Shopify | 免费 3 个 AP 来源订单 | ① |
| 商家 | Q2 = 没有 / 计划做 | 1v1 专家诊断 | ② |
| 供应商 | 全部 | 定制帆布袋 | ③ |
| 服务商 | 全部 | AP 定制扇子 | ④ |

## ⚠ 转盘不是随机数

**奖项在问卷提交那一刻就已确定**，转盘只是过程体验，动画必然停在预定格上 ——
这是 SOP 第一节「核心逻辑」的原文要求。盘面照常展示 4 格，所以看起来像真抽奖。
**后来维护的人不要把它改成 RNG。**

之所以这么做不算欺骗：100% 中奖、不涉及金钱，而奖项差异是**资格差异** ——
「免费 3 个 AP 来源订单」只有真有 Shopify 店的商家才用得上，发给没店的人是浪费。

落点算法：盘面第 i 格中心在顺时针 `i*90+45` 处，指针固定在正上方，
所以旋转角 = `360*6 + (360 - (i*90+45)) + 抖动`。抖动 ±30° 是为了别每次都停正中间
（那样太假）；抖动取自时间戳而非 `Math.random`，可复现。

## 数据落库

### 现在是怎么落的

```
手机填完 → ① 写本机 localStorage（一定成功）
         → ② POST /api/survey 给发二维码的那台电脑
              成功 → 追加进 E-survey/_data/survey-YYYY-MM-DD.jsonl
              失败 → 进本机补传队列，下次打开页面自动补上
```

**②失败绝不会挡住抽奖。** 现场参与者不该为我们的网络问题买单 ——
推送失败照样进转盘、照样出中奖页，那条记录只是排队等补传。

### 为什么落在那台电脑上，而不是直接连云数据库

手机能打开这个页面，就说明它和这台服务器在同一个局域网、同一个 origin。
POST 走的是**和加载页面完全相同**的那条链路 —— 页面打得开，接口就通，
不引入任何新的失败模式。手机直连云要过展会 WiFi 的外网出口，
那是现场最不可靠的一段，而它一断就是静默丢线索。

要上云的话，正确的接法是把本机这份 JSONL 当作**权威副本**，
另起一个同步进程往上推（见下「要不要上云」）。

### 为什么是 JSONL 不是 JSON 数组 / SQLite

追加写。进程被杀、笔记本断电，最多丢没写完的最后一行，不会像
「读出整个数组 → push → 整份写回」那样把已有的几百条一起写坏。
展会一天几百条，SQLite 带来的查询能力用不上，却多一个原生依赖。

### 为什么写入侧不查重，去重放在读取侧

前端补传队列会重发同一条记录。如果写之前要先读一遍全量文件查重，
**读失败就会连带写失败** —— 写入路径必须极简且永不因逻辑失败。
重复行留在文件里，`list` / `export` 时按 `device + ts` 去重。

### 读写权限是不对称的（重要）

| 接口 | 谁能用 | 说明 |
|---|---|---|
| `POST /api/survey` | 任何局域网设备 | 手机就是它的客户端 |
| `GET /api/survey/list` | **仅本机**，或带 token | 返回 JSON，含联系方式 |
| `GET /api/survey/export` | **仅本机**，或带 token | 返回带 BOM 的 CSV |

展会 WiFi 是公共网络，同网段的任何人都能摸到 8099 端口。里面是参与者的
微信号 / 手机号，**不能让路人整包拉走**。

「本机」认的是回环 + 本机各网卡地址 —— 操作员很可能直接用二维码里那个
`http://192.168.x.x:8099/` 打开管理页而不是 localhost，只认 `127.0.0.1`
会把自己挡在门外，而且是**静默降级成「仅本机 localStorage」**，
恰好是这套改造要消灭的那个错误口径。

要在**手机**上看全场汇总：

```
set AP_SURVEY_TOKEN=随便一串   &&  node _serve.js
手机开  http://<IP>:8099/E-survey/?admin=1&k=随便一串
```

### 现场怎么用

服务启动时会把这几个地址直接打出来：

```
问卷落库:   …\E-survey\_data  （今天已有 N 条）
现场汇总:   http://localhost:8099/E-survey/?admin=1
按天导出:   http://localhost:8099/api/survey/export?date=2026-08-21
```

管理面板会**明确标注数据口径**：读到服务端就显示「全场汇总（所有手机）」，
读不到就退回「仅本机」并标红说明为什么 —— 上一版只有本机一种口径却没说，
很容易把一台手机的 3 条当成全场 3 条。

导出按钮也跟着口径走：能读服务端时是「导出 CSV（全场）」，
否则是「导出 CSV（仅本机）」。

清空按钮**只清本机**。服务端那份是权威副本，不给前端一个删库按钮 ——
现场误触一下线索就没了。真要清就去删 `_data/` 下的文件。

### 云端：飞书多维表格（已接好）

表已经建好了：**AP 展会问卷线索 → 「线索」表**，13 个字段，现在 0 行。
`_lark.json` 存着 `app_token` / `table_id` / 打开链接。

```
node _lark-init.js            建表（已经跑过，不用再跑）
node _lark-init.js --check    检查表还在不在、字段有没有缺
node _sync-lark.js --dry-run  只算不写，先看清这次要动什么
node _sync-lark.js            同步
node _sync-lark.js --date=2026-08-21   只同步某一天
```

**只在展后手动跑，不做实时同步。** 实时等于把现场链路绑上外网，
风险换来的只是「早几个小时看到」。而且同步走用户身份（`useUAT`，需要 OAuth），
本来就跑不了无人值守的定时任务。

#### 表里多两列是给销售的

`跟进状态`（待跟进 / 已联系 / 已加微信 / 无效线索 / 已成交）和 `跟进备注`。

> ⚠ **同步永远不写这两列**（白名单在 `_lark-schema-def.js` 的 `SYNC_FIELDS`）。
> 如果同步一并覆盖，第二次跑就把销售填的跟进记录抹了 —— 而且是静默抹掉，
> 等发现时已经追不回来。这条有专门的验收：先模拟销售填上，再改本地数据逼同步去写
> 那一行，然后断言「联系方式更新了、跟进两列还在」。

#### 幂等键是凭证编号

跑第二遍不会重复插入，只把变了的字段补上，而且**只发变了的那几个字段** ——
少一次写就少一次覆盖的机会。`record_id` 不变（是原地更新，不是删了重建）。

#### 代码会翻成人话

JSONL 里存的是 `role='A'` / `shopify='yes'` / `gmv='>50k'` 这种给程序看的代码，
销售在表里看到 `A` 是没有意义的。映射表在 `_lark-schema-def.js`，
**只在同步时做，落盘那份保持原样** —— 原始值才是可回溯的。
空值不写进去，让它在表里保持为空（可以按「为空」筛），比塞一个「（未问）」的假选项干净。

#### 两个坑

- **挂不进 wiki 知识库** —— 那一步要 `wiki:wiki` scope，这个凭证一直缺（报 99991672）。
  要放进知识库只能人工拖一下。
- **这个凭证没有「删记录 / 删表」的接口**，写进去就只能到 UI 里人工删。
  所以验收用的是一张**一次性表**（名字带「可删」），不脏真正的「线索」表。

#### 本地备份仍然建议做

云端解决的是「展后随时可查」，解决不了「笔记本当天就坏了」——
同步是展后才跑的。真要保当天的数据，还得加一个每 N 分钟把 `_data`
拷到另一块盘的脚本（五行）。**这个还没做**，见待办。

## 防重复

SOP 说「规则由产品定」。现在实现的是**同一设备仅首次有效**
（`app.js` 顶部的 `ONE_PER_DEVICE`，想放开改成 `false`）。
重复进入时**直接回显上次的中奖页** —— 正好满足 SOP「页面保留可截图/可回显」那条。

设备号存在 localStorage，清了浏览器数据就能再抽一次。
有了服务端之后**按联系方式去重是做得到的了**（一个接口调用的事），
但还没做 —— 见待办。

## 二维码

大屏左下角那枚小标点开就是二维码，指向本页。二维码是**现场生成的**
（`../E-监控台-V1版式/qr.js`，自己写的最小 QR 编码器，零网络依赖，不调任何在线接口）。

地址走 `_serve.js` 的 `/__lan` 实时探测（UDP connect 选出口网卡），
不再写死 IP —— 写死的是 DHCP 地址，换网络就变成「码扫得出来、打开连不上」。

## 实测

验收脚本：`../E-后台-可操作版/_checks/ckSurvey.js`（60+ 项）
+ `ckQr.js`（扫码全链路里也走一遍问卷）。两个都在 `run-all.js` 里。

| 项 | 结果 |
|---|---|
| `node --check` | 过 |
| console 错误 | **0** |
| **首屏不露奖品** | 四个奖品名在首屏可见文本里**全部查无**；`.plist` 节点已删除（不是 CSS 藏起来） |
| **首屏仍有参与理由** | 「抽奖」「100% 中奖」都还在 |
| **奖品延后到转盘** | 转盘四格四种底色都画出来了，四个奖项定义完整 |
| **不自动跳题** | 选中后等 **1200ms**（旧自动跳是 180ms）仍停在同一题 |
| **点了才走** | 点「下一题」后确实进到 Q2 |
| **禁用态** | 未选时 `btnNext.disabled=true`；选中后变可点；选填题空着也可点 |
| **换身份清脏字段** | A 答完 Shopify/GMV → 退回改 C → 记录里 `shopify=""` `gmv=""`，`size` 正常 |
| **落到服务端** | 按联系方式从 `/api/survey/list` 读回，凭证号 / 奖项 / 分支字段逐项一致 |
| **服务端补入库时间** | `srvTs` 存在（手机时钟不可信时用它） |
| **推送失败不挡流程** | 拦掉 POST 后照样进转盘，记录进补传队列（长度 1），服务端确实还没有 |
| **补传** | 恢复后重开页面 → 队列清零，那条出现在服务端，总数 +1 |
| **重复提交** | 同一条 POST 两次 → 列表仍只出现 1 次（读取侧按 device+ts 去重） |
| **坏输入** | 非法 JSON→400 · 缺凭证号→400 · 超长联系方式截到 200 字符 · 白名单外字段被丢 · >8KB 被掐断且不留记录 |
| **读权限** | 回环可读；构造的外部 IP 不带 token 读不了、token 错也读不了、token 对才放行 |
| **按天导出** | 200 · `text/csv` · `attachment` · 开头有 UTF-8 BOM · 行数 = 当天条数 + 表头 · 畸形 `date` 参数不穿越目录 |
| 五条路径判定 | **5/5 全对**（判定规则在测试里独立重写一遍做对比，不复用被测代码） |
| 转盘落点 | 5/5 都停在预定格（按旋转角反算落在指针下的格号，与预定格号比对） |
| 中奖页回显 | 重开页面直接显示上次奖项 ✓ |
| 手机 390px | 无横向溢出 |
| 转盘文字 | 四格全部正面朝上（左半边曾经是倒的，已修） |

> **未验**：真手机开 `?admin=1` 应该被拒（403）。本机造不出「非本机来源」的请求 ——
> 从这台电脑发出去的包，源地址一定是本机某个网卡地址。所以这条只测到了判定函数
> `canRead()` 本身，端到端仍然需要拿一台手机试一次。

## 待办

1. **`_data/` 的当天自动备份**（每 N 分钟拷到另一块盘 / 网盘目录，五行脚本）——
   飞书同步是展后才跑的，救不了「笔记本当天就坏了」

3. **按联系方式服务端去重** —— 现在有服务端了，做得到但没做
4. 联系方式没做格式校验（手机号/微信号规则不同，且现场输入千奇百怪，
   过严会挡住真实用户 —— 建议只做长度与非空校验，就是现在这样）
5. 奖品库存没做（比如帆布袋发完了要能切成别的），SOP 也没提，需要产品定
6. 转盘没有音效（大屏有 `APAudio`，这里是独立页面没接）
7. 把「线索」表挂进 wiki 知识库 —— 缺 `wiki:wiki` scope，只能人工拖

## 自检口

```js
APSurvey.records()      // 本机全部记录
APSurvey.pending()      // 还没推上服务端的队列
APSurvey.flush(cb)      // 手动补传，cb(已发条数, 剩余条数)
APSurvey.prizes         // 奖项定义（含盘面顺序）
APSurvey.decide({role:'A',shopify:'yes'})   // 判定规则，返回盘面格号
APSurvey.reset()        // 清掉「已参与」标记，可再抽一次
APSurvey._canNext()     // 「下一题」现在能不能点（给验收脚本用）
```

服务端：

```
curl http://localhost:8099/api/survey/list                   # 全场 JSON
curl http://localhost:8099/api/survey/list?date=2026-08-21   # 某一天
curl -O http://localhost:8099/api/survey/export?date=2026-08-21   # CSV
```

## 这个目录里的文件

| 文件 | 是什么 |
|---|---|
| `index.html` / `app.js` | 问卷 + 转盘（零第三方库、零网络依赖） |
| `_data/` | 落库目录，按天一个 `.jsonl`。**权威副本**，别手改 |
