# 方案 D · 诊断墙

> **一句话定位**：输入你的域名，看看 AI 现在读到了你店里的多少。

A / B / C 三个方案讲的是「我们很牛」。这一块讲的是「**你有问题**」——
用三项观众自己能复核的检查制造缺口，当场把围观的人变成线索。
它也是四个方案里**唯一跟现场互动活动打通**的一块。

---

## 1. 设计意图

### 1.1 为什么是「诊断」而不是「炫数字」
DTC 商家在展会上看到别人家的大数字，第一反应是「跟我有什么关系」。
把行业数字（Adobe 的 66%）挂成顶部横条做**参照系**，再把观众自己的域名算成一个
0~100 的分数放在旁边，**关系就成立了**：66 是别人，41 是你。
缺口一出现，BD 才有话可讲，观众才有理由留联系方式。

顶部横条是浅底卡片、模拟数字全部深底 —— 这是规格 §7.4 要求的「公开数据与模拟数字
必须视觉分区」，不能让真数据给假数字背书。

### 1.2 三项检查为什么只有三项
只做**能被观众当场拿手机复核**的项：

| 检查项 | 取值 | 复核方式 |
|---|---|---|
| `robots.txt` 是否放行 AI 爬虫 | 放行 / 部分放行 / 未放行 | 打开 `域名/robots.txt` 自己看 |
| 商品页结构化数据完整度 | 百分比 | 看商品页 JSON-LD 的必填字段 |
| 多语言覆盖 | N / 8 个市场 | 数一下自己上线了几个市场 |

**绝不输出**「你在某个 AI 助手里排第几」这类无法核实、必然误诊的结论 —— 那是这块屏
最大的法律与口碑风险（详见 §4.1）。

综合分 = `robots 30 分 + 结构化 45 分 + 多语言 25 分`。权重写死在 `app.js` 的
`makeDiagnosis()` 里，**现场立牌上印同一套**，观众可以自己复算。可复算才不叫玄学。

### 1.4 跟现场 SOP 的对齐
奖项判定逐条落在 `app.js` 的 `classify()` 里，与
《AP 展会互动 · 问卷分流 + 大转盘 2026-08-18 v2》第三节完全一致：

| 问卷分流 | 转盘停在 | 屏上表现 |
|---|---|---|
| 商家 + 正在运营 Shopify | 免费 3 个 AP 来源订单 | 上主卡，出分数 |
| 商家 + 没有 / 计划做，但有独立站 | 1v1 专家诊断 | 上主卡，出分数 |
| 商家 + 无独立站 | 1v1 专家诊断 | **不上主卡**，只进「另有 N 位无独立站观众参与」 |
| 供应商 | 定制帆布袋 | 同上 |
| 服务商 | AP 定制扇子 | 同上 |

**没有域名就不产出分数** —— 这是「绝不误诊」的一部分，不是偷懒。
四个奖项在右栏二维码旁常驻列出，观众抬头就知道能抽到什么。

## 2. 快捷键

统一那套（规格 §6）全部实现，**外加 `S`**：

| 键 | 作用 |
|---|---|
| **`S`** | **模拟一次观众扫码进入（本方案的核心演示动作）** |
| `空格` | 暂停 / 继续 |
| `B` | 人工触发一个大单（BD 讲到关键处配合用） |
| `N` | 触发一个普通单 |
| `K` | 触发里程碑全屏庆祝 |
| `M` | 静音 / 取消静音 |
| `1` `2` `3` | 速率 ×0.5 / ×1 / ×3 |
| `G` | 调试网格（`?debug=grid` 同效） |
| `H` | 展馆音频模式（切 100Hz 以下 + 补 2~4kHz） |
| `A` | 环境音床（本方案默认关） |
| `F` | 全屏 |
| `R` | 重置 |
| `?` | 显示 / 隐藏快捷键图例 |

### `S` 键的手感是专门调过的
- 按下 → 立刻进审核队列（左上角 `审核队列 N` 会 +1，BD 可以指着说"在审核"）
- **1.6 秒**后上主卡（自动到达的观众走 5~10 秒，见 §4.2）
- 如果当前主卡还在停留期，剩余停留会被压到 **2.2 秒**，不让人干等
- 连按只保留最近 4 张，多按的直接丢 —— 讲解节奏优先于"每张都播完"
- 实测连按 10 次 / 30 次：卡片不堆积，DOM 节点数恒定 529（见 §6）

## 3. 已知取舍（都是真取舍，不是没做）

### 3.1 主角字号只到屏高 25%，没到规格的 30~50%
综合分字号 413px，cap height ≈ 293px ≈ **屏高 27%**（三位数时 3 槽 × 0.54em = 669px，
已经吃掉卡内 820px 可用宽度的 82%）。

要到 30%+ 就得把体检卡从 638px 抬到 700px 以上，那么下方的「已诊断」墙只剩 2 行 —— 而
那面墙是这个方案的社会证明（"已经有 80 多家在这儿测过了"），比多 3% 字号值钱。

> **如果验收时要求必须 30%+**：把「已诊断」列表整块挪到右栏底部（替掉订单播报），
> 左栏就能给到 760px 卡高、分数字号 500px（cap 355px = 屏高 33%）。这是一次纯搬移，
> 半小时能改完。

### 3.2 爬虫计数器 cap 只有屏高 8.8%，不是 22%
这一条是**物理上做不到**，算式如下：

```
metrics.crawls = 420,xxx,xxx  ->  9 位数字 + 2 个逗号 = 11 个字符
固定字宽槽：数字 0.54em、逗号 0.30em  ->  总宽 5.46em
要 cap height = 屏高 22% = 237px  ->  字号 = 237 / 0.71 ≈ 334px
       ->  总宽 = 5.46 × 334 = 1824px = 屏宽的 95%
```
1824px 放不进 35% 栏（672px），连整个右半屏加沟槽（824px）都放不下。
唯一能满足 22% 的做法是把它做成**通栏横条**，那就跟 45 / 35 两栏版面冲突。

实际取值：字号 134px（总宽 732px，向左溢出沟槽 60px，离左栏还有 92px 余量），
cap ≈ 95px ≈ 屏高 8.8%，与主角字号之比 **32%**（规格 §4.3 建议 35~40%，略低于下限）。
守住的是"配角明显小于主角"这个意图。

> **如果一定要 22%**：两个选项 ——
> (a) 计数器改通栏，左右两栏下移；
> (b) 显示 `metrics.session.crawls`（本场新增，7 个字符），可以做到 cap ≈ 屏高 16%。
> 但 (b) 会丢掉"累计 4.2 亿次"这个最有冲击力的量级，我不建议。

### 3.3 其它取舍
- **审核延迟原型是缩短的**：`S` 键 1.6 秒、自动到达 5~10 秒。正式版一律 5~10 秒
  **且必须人工放行**（§4.2）。缩短只为讲解节奏，`REVIEW_KEY_MS` 一个常数就能改回。
- **三项检查全是假数据**。分数公式的 30/45/25 权重是我拍的，**上会前要产品确认**。
- **无独立站的观众不上主卡**，只进计数。代价是主卡上只会出现两种奖项（AP 订单 /
  1v1 诊断），帆布袋和扇子只在右栏奖池里露脸。换来的是"绝不无域名出分"。
- **分数分布是有意偏低的**：均值 46.5，62% 落在 50 分以下，1.1% 上到 80+。
  留 1% 高分是刻意的 —— 一面墙全是低分，懂行的商家会怀疑被操纵。
- **分数动画是「从 0 向上滚」**，不是"上一张的分数滚到这一张"。后者必然出现数字倒退
  （规格 §4.2 明令禁止），前者永远单调向上，还顺带有"仪表盘充能"的观感。
- **待机示例卡每 12 秒换一张，每张都挂 `SAMPLE · 示例`**；「已诊断」列表开屏用 3 条
  示例种子（前缀「示例 ·」），会被真实卡逐条挤出去。绝不让观众误以为是真实客户。
- **订单播报开屏是空的**，第一笔最多等 117 秒（引擎保证的最大空窗）。空行不占位、
  显示一行「等待下一笔 AI 引荐订单…」。想立刻填满就按 `B`。
- **超宽屏（21:9 / 32:9）留黑边**，没做切栏。stage 整体等比缩放，1280×720 到
  3840×1080 都不炸版。
- **人声用浏览器 `speechSynthesis` 顶着**，正式版必须换离线合成音频（§5）。
- **二维码是 Canvas 画的假图案**（确定性哈希，无任何库），上会前必须换（§5）。

## 4. 现场风险与对策（这是本方案最大的隐患，逐条看）

这块屏跟另外三个方案有一个本质区别：**它对着真实观众的真实资产下判断**。
判断错了不是"演示效果不好"，是当场得罪人、甚至留下书面证据。

### 4.1 误诊 —— 最贵的风险
**风险**：把「AI 读不到你的店」说成结论，商家回去一查发现不是那样，
这块屏就从"专业"变成"忽悠"，而且是被截图传播的那种。

**对策（已在原型里落实）**
1. **只做三项可客观核实的检查**，每项都能让观众当场用手机验证。
2. **绝不输出排名类结论**（"你在 ChatGPT 里排第几"）—— 无法核实、无法归因、必然误诊。
3. 卡上常驻**检测时间**与**检测项定义**一行小字（`检测时间 14:23:07 · 检测项：
   robots.txt 放行 / 商品页 JSON-LD 必填字段 / 已上线市场数`），说明这是某一时刻的快照。
4. **没有域名就不出分**（无独立站的观众只计数）。
5. 分数**权重公开**，现场立牌印同一套算式。

**还需要补的**：抽样页数、检测超时口径、以及"结构化数据完整度"的字段清单，
要在立牌上写清楚（例如：抽样 20 个商品页，检查 name/image/offers/price/availability/brand
六个必填字段）。这一条**上会前必须定稿**，否则口径对不上就是误诊。

### 4.2 脏话 / 竞品名上墙
**风险**：观众在问卷里填的域名、店名会上大屏。有人会故意填脏话、竞品域名、
甚至恶意链接。直连上屏 = 把大屏交给陌生人。

**对策**
1. **绝不做直连上屏。** 原型已经实现「提交 → 审核队列 → 放行 → 上屏」三段式，
   左上角常驻 `审核队列 N · 已拦截 M`。
2. **延迟 5~10 秒 + 人工放行**：正式版必须有一名工作人员盯一个放行界面，
   点一下才上屏。原型里自动到达走 5~10 秒随机延迟（`S` 键为讲解节奏缩到 1.6 秒）。
3. **敏感词 / 竞品名过滤**：`app.js` 里的 `isClean()` + `BLOCKLIST` 是骨架，
   原型只放了三个占位词。上会前必须接完整词库（脏话、竞品品牌名、政治敏感词、
   带 `punycode` 的仿冒域名），并且**过滤在放行界面之前跑**，被拦的直接不进队列。
4. **域名白名单式校验**：只接受 `^[a-z0-9.-]+\.[a-z]{2,}$`，长度上限 63，
   拒绝 IP、端口、路径、查询串。
5. 兜底：现场留一个「一键清屏 / 切回示例模式」的物理动作（原型里就是 `R`）。

### 4.3 依赖网络 —— 展馆网络不可信
**风险**：真检测服务要发 HTTP 请求。展馆 WiFi 抽风时，观众扫码填完问卷，
大屏转半天出不来分数，比不做还难看。

**对策**
1. **预置知名站点的缓存诊断结果做兜底**：提前离线跑一批（20~50 个公开可查的
   知名 DTC 站 + 主办方展商名单里的站），结果打包进本地。断网时命中缓存直接出分，
   卡上标注「缓存结果 · 检测于 X 月 X 日」。
2. **检测超时 3 秒硬上限**，超时不出分、改出「本次未取到，请扫码留联系方式，
   我们把完整报告发给你」——**超时反而是更好的转化话术**。
3. 大屏本体（本方案的 index.html）**已经是零网络依赖**：无 CDN、无远程字体、
   无远程图片、无 `fetch`。断网只影响真检测服务，不影响这块屏继续跑。
4. 现场备一个 4G 热点专供检测服务，跟展馆 WiFi 物理隔离。

### 4.4 隐私
**风险**：现场收集数据 + 大屏公开展示，很容易越线。

**对策**
1. **只收域名，绝不要后台授权 / API Key / 店铺读权限**。三项检查全部只用公开可抓
   的信息（`robots.txt`、商品页 HTML、已上线市场），不需要任何授权。
2. **现场立牌明写**：「您输入的域名仅用于生成本次诊断，不留存、不用于其它用途。」
3. 联系方式（问卷 Q4）与域名**分表存**，大屏侧只拿到域名和分数，拿不到联系方式。
4. 大屏上**不显示任何联系方式**，一个字都不显示。
5. 展后线索导出要有明确的保留期与删除责任人（跟 SOP 第四节的"数据落库"一起定）。

### 4.5 需要一个真能跑的轻量检测服务（上会前最大的一块工程量）
原型里三项检查全是假的。真版最小可用形态：

```
POST /diagnose { domain }  ->  { robots, schema, markets, score, at, cached }
  1) 取 <domain>/robots.txt (HTTPS)        判断 GPTBot / ClaudeBot / PerplexityBot /
                                           Google-Extended 的 Allow / Disallow
  2) 取 sitemap 抽 20 个商品页             解析 JSON-LD，统计六个必填字段的完整度
  3) 探测 /xx-yy/ 或 hreflang              数已上线市场
  硬性要求：整体 3 秒超时、并发上限、结果缓存、域名格式白名单、
            拒绝内网地址（SSRF）、每设备限流
```
**估算**：一个人 3~5 天（含缓存兜底与限流）。这是整个方案能不能上会的**唯一硬前提** ——
没有它，`S` 键就只能演示，不能真接观众。
