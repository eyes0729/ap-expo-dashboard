# 方案 E · AI 渠道后台（可操作版）

> **平行版本。** `E-监控台-V1版式` 与 `E-运营监控台` 原样保留，A/B/C/D 与 C-LED 两版一行未动。
> 打开：`http://localhost:8099/E-后台-可操作版/index.html`
> 切主题：**顶栏右侧按钮**，或按 **`D`**。`?` 看全部快捷键。

## 这一版和 V1 版式的定位差别

| | `E-监控台-V1版式` | **这一版** |
|---|---|---|
| 是什么 | 展会大屏**画面** | **真的后台** |
| 有没有应用级导航 | 没有（kiosk 那一路） | **有侧栏** |
| 能不能点 | 只能按快捷键 | 筛选 / 排序 / 搜索 / 导出 / 抽屉 / 暂停 |
| 有几个页面 | 一屏 | **五页**：实时看板 + AI 订单 + AI 读取记录 + 店铺 + 设置 |
| 主题 | 五套，屏上无入口（内部的事） | **两套，顶栏有入口**（后台里主题是用户自己的偏好），**贯穿到全屏地球** |
| 观看距离 | 3~5 米 | **1~3 米，让商家上手点** |

> **这一版的验收判据是「拟真」**：每一个看着能点的东西都必须真的有反应。
> `_checks/ckReal.js` 就是为这条写的 —— 75 项，判据不是「点了没报错」，
> 而是**点完之后有可观测的状态变化**（DOM 类名 / 表格行数 / 排序方向 /
> 引擎状态 / 下载事件 / 页面切换）。点一个控件而什么都没变，它就是假的。

版面尺寸不是我拍的，全部照 `参考-SaaS后台\_关键度量.md` §16 的中文后台实测：
**侧栏 232（TDesign）· 顶栏 57（TDesign）· 内容内边距 24 · 卡片间距 16 · 圆角 6 · 阴影几乎无**。

```
高度账（1080）  顶栏 57 + 内容 1023
               内容内边距 24×2 = 48 → 可用 975
               KPI 96 + 地图区 320 + 订单 268 + 日志 243 + gap 16×3 = 975 ✓
宽度账（1920）  侧栏 232 + 主区 1688；主区内边距 24×2 → 可用 1640
               地图卡 800 + gap 16 + 右侧板 824 = 1640 ✓
               订单 9 列合计 1640 ✓　日志 7 列合计 1640 ✓
```

## 这一轮点名要改的七条，逐条对照

### 1. 订单渐入回到方案 C 原版的动画

**根因**：V1 那版说"取方案 C 原版"，但实际把两个核心都简化掉了。

| | 方案 C 原版 | V1 版式 | **这一版** |
|---|---|---|---|
| 翻页单位 | 每**字符**一格（115 格） | 每**列**一格（7 格） | **每字符一格（94 格）** |
| 立体翻板 | `perspective(560px) rotateX(-76°→0°)` | **完全没有 transform** | **同 C 原版** |
| 波长 | 115×21ms ≈ **2.4 秒** | 7×21ms = **147ms** | 94×21ms ≈ **2.0 秒** |
| 字符鼓 | 同类字符鼓（数字/字母/标点） | 有 | 有（+ CJK 鼓） |

等 55 秒来一笔订单、只闪 147ms —— 这就是"看着假"的来源。

**实测波形**（按 `B` 后连续抓帧，`X` = 该格正在翻）：

```
  120ms  |XXXXX ........................... .....
  420ms  |..... XXXXXXXXXXXX............... .....
  720ms  |..... ...........XXXXXXXXXXXXXX.. .....
 1020ms  |..... ........................... .XXXX
 1320ms  |..... ........................... .....       XXX XXXXXXXX.
 1620ms  |..... ........................... .....       ... ......... XXXXXXXX XXX..........
 1980ms  |..... ........................... .....       ... ......... ........ ......XXXXXXX XXXXX..
```

波从行首整齐扫到行尾，左边先落位、右边还在翻 —— 机场牌的读法。
乱码按字符类别翻（中文位翻出「西班典」、数字位翻数字），不是随便糊一片。

> 一处与 C 原版**故意不同**：C 是整行 115 个等宽格，靠等宽字体保证跨行列对齐；
> 这一版是有列宽的后台表格，列对齐由 `.c` 的固定 px 宽保证，**不依赖字体** ——
> 所以日文商品名（`リネンコットンマグ`）也不会把后面的列顶歪。

### 2. 两个流的速率

**实测**（22 秒采样，V1 版式）：

| 流 | 实测 | 一行在屏上活多久 | 判断 |
|---|---|---|---|
| AI 读取日志 | 9 条/秒 | **1.2 秒**（11 行表） | 快到糊 —— 6 个字段人读不完 |
| AI 订单 | **1.1 笔/分钟** | 5.5 分钟（6 行表） | 慢到静止 |

**两个速率是反的**，这才是根因。处置分开：

- **订单慢是真实的**。`ordersPerMin` 是引擎的产品数据口径（README 待办说过要产品确认量级），
  我不动它。真后台的订单本来就不会秒秒钟来。修法是让那一笔**值得等**：
  2 秒翻牌 + 4.2 秒地图播报。
- **日志快才是真缺陷**。这一版数据层照全速收（地图打点要它），
  **上屏每 6 条只显示 1 条** → 实测 **1.53 行/秒，8 行表约 5.2 秒换一遍**，一行读得完。
  面板头仍然写真实速率「每秒约 38 个页面」——**计数是真的，显示是采样的**，这也是真实后台日志面板的做法。

### 3. 新订单在地图点位弹播报卡

`国家 · 城市` / `金额` / `哪个 AI 带来`，带引线牵向点位，停 4.2 秒。
3 张卡预建循环复用（动态 append 会破坏 DOM 恒定），最多同时 3 张。
靠右 / 靠上时自动翻向，卡片永远留在地图框内（实测 `inside: true`）。

> 修过一个时序 bug：订单点原先只活 1.1 秒，而卡片停 4.2 秒 ——
> **后 3 秒引线指向一片空白**。现在订单点活到卡片消失为止（扩散圈仍只在头 1.1 秒，
> 否则会扩成一个大圆）。

### 4. 输出支持筛选

数据层与渲染层是分开的 —— 这样筛选才能筛到**屏外**那些行，导出也才是导全部：

| 层 | 内容 |
|---|---|
| 数据 | `ordBuf` 最近 80 笔 / `logBuf` 最近 120 条 |
| 视图 | 按筛选 + 排序算出来，取前 6 行 / 8 行上屏 |

- **订单**：按 AI 助手 / 国家 / 订单规模筛，表头点击排序（时间/订单号/店铺/国家/来源/金额），顶栏搜店铺或商品名
- **日志**：按 AI 助手 / 结果筛，可暂停滚动
- 筛完没结果给**真的空态**，不是留一张空表
- 下拉选项**跟着数据长**（后台不该列出一个「筛完是空」的选项）
- 导出 CSV 导的是当前筛选 + 排序后的**全部** 63 笔，带 UTF-8 BOM（不加 Excel 打开中文全乱码）

**打开就有 63 笔历史**，不是 6 笔 —— 只铺 6 笔的话筛选、排序、导出全都没有意义（实测「按国家筛」只剩 1 笔）。

> `peekOrders` 有 62 笔硬上限（实测：传 200 / 600 / 1500 / 4000 都是同一批）。
> 直接拿它们当历史有个坑：这些 id 真到达时会被去重挡掉，订单流冻死。
> 所以历史单的 id 加了 **500000 偏移** —— 它们是独立的历史记录，真实流每一笔都还能进来。
> 订单号因此必须取 **6 位**，4 位的话偏移被截掉，历史单和真实单会撞出同一个号。

### 5. 两套主题，主题色保留，屏上有入口

| | 深色科技风（默认） | 浅色科技风 |
|---|---|---|
| 页面底 | `#08090B` | `#F1F2F4`（店匠实测） |
| 面板 | `#101216` | `#FFFFFF`（四家一致） |
| 分隔线 | `#1C1F25` | `#E8E9ED`（店匠实测） |
| 正文 / 次级 | `#F7F8F8` / `#9CA3AF` | `#222222` / `#6C7175`（店匠实测） |
| 冷强调（AI 读取） | `#00D3A7` | `#008E74` |
| 暖强调（订单） | `#FFB86B` | `#B26A16` |

**主题色一分没改**，浅色下只是压深了一档 —— 原值是给深底反白设计的，
放到白底上对比度只有约 1.6:1，等于看不见。色相是同一对。

浅色的每一个中性色都来自 `_关键度量.md` §15「中文后台的颜色（全部浅底）」实测表，
不是我调的。切换时**地图底图会重烤**（陆块与市场点也是主题色，只改 CSS 变量它不会变），
sparkline 同理。

> **一条要让你知道的冲突**：04 线的调研结论第 1 条是「别为真实感翻浅色 ——
> 3 米外白底晃眼反光」。但它的第 4 条是「真要做浅色，只做**模拟商家自己后台**那一屏
> 当认知锚点」。两套主题可切换正好落地的是第 4 条：
> **深色 = 朝外的、3 米外不反光的那块屏；浅色 = 让商家上手点、"我每天干活的地方"那块屏。**
> 所以现场朝外的主屏建议仍用深色，浅色留给展台内侧和截图。

### 6. 扫码入口的悬浮感

**根因**：V1 那版是 `panel2 #15181D` 压在 `panel #101216` 上、**零投影** ——
亮度差只有一档，所以"和背景融为一体"。

这一版悬浮感有三个来源，缺一个都不行：

1. **专属底色 `--lot`**（深色 `#1E242C`，比侧栏底 `#0C0E12` 亮好几档）
2. **双层投影 + 1px 描边环**
3. 深色下再叠一圈极淡的 accent 外发光，把它从纯灰里拉出来

外加左侧 3px accent 竖条 + 实心 accent 图标块。悬停整块上浮 3px 并加强发光。

位置也挪了：**从左下角挪到侧栏底部**。V1 那版压住订单表最后一行，
而侧栏底部本来就是后台放「帮助 / 活动」入口的地方。二维码卡从侧栏往右浮出，不遮表。

### 7. 后台家具（这一版"是后台"的部分）

| 家具 | 做了什么 | 是不是真的 |
|---|---|---|
| 侧栏导航 | 实时看板 / AI 订单（带数量角标）/ AI 读取记录 / 店铺 / 设置 | 只有「实时看板」有内容，其余是骨架 |
| 时间范围 | **开幕至今 / 累计** | **两档都是引擎真实口径**（`session.*` 与全量），不造假 |
| 搜索 | 按店铺名 / 商品名 / 订单号，180ms 防抖 | 真的 |
| 导出 CSV | 12 个字段，含原币金额与币种 | 真的 |
| 详情抽屉 | 点任意订单行，12 个字段 | 真的 |
| 反色 KPI 卡 | 第一张整块填实主题色 | 焦点手段照 `_关键度量.md` §18①（`B2` 做法，成本就是一个背景色，不靠字号砸） |

渠道占比改用引擎的 **`platformBreakdown()`（权威权重）**，不再拿 `peekOrders` 取样估 ——
V1 那版 62 笔取样会把 Google 算成 4.8% 而真实权重是 14%。
国家基数仍用 `APGeo.MARKETS` 自带的 `weight`（金额是重尾分布，取样会让权重 6 的加拿大掉到 1%）。
两边的增量都走真实订单，所以是活的。

## 第二轮改动（五条）

### 1. 世界地图被压扁

**根因是几何**：点阵是 64 列 × 26 行，塞进 1100 × 246 的画布后格子变成
**17.19 × 9.46 —— 长宽比 1.82，横向拉伸近一倍**，所以大陆看着是扁的。

| | 改前 | 改后 |
|---|---|---|
| 地图卡 | 1100 × 246 | **800 × 276** |
| 格子 | 17.19 × 9.46 | **12.47 × 10.62** |
| 长宽比 | **1.82** | **1.17** |

挪出来的 300px 给了右侧的饼图 —— 两个需求正好互相成全。

### 2. 按国家 / 地区改成可 hover 的甜甜圈图

- 扇区与图例**双向联动**：hover 任一侧，另一侧同步高亮、其余压暗
- 高亮的扇区沿角平分线往外挪 5px（比单纯提亮更容易看出是哪一块）
- 中心固定三行：占比 / 国名 / 金额；不 hover 时是总额 / 总成交额 / N 个国家
- 扇区 path 建一次不再增删，DOM 恒定

分类数据本该用分类色，但六种色相会把「简洁科技风」搅花。
真实后台（TDesign / antd 的默认饼图）走的是**品牌色的明度阶** —— 这里照做，
「其他」固定用最末一档的中性灰，一眼能看出它不是某个具体国家。

> `#pieSvg` 必须 `pointer-events:none` 而 `path` 是 `auto` ——
> 否则甜甜圈的洞和四角空白会把 hover 吃掉。

### 3. 四张指标卡都得会动

| 卡 | 改前 | 改后 | 实测 |
|---|---|---|---|
| 成交额 | 已有 +$xxx 浮起 | 同 | 10 虚拟分钟变 10 次，浮起 10 次 |
| 订单 | 只有数字默默变 | **加 +N 浮起** | 10 虚拟分钟变 10 次，浮起 10 次 |
| AI 读取商品页 | 显示 `crawlsPerSec` 速率 —— 一秒内几乎不变，**看着像卡住** | **改成累计已读页数**（约 38/秒） | 10 虚拟分钟变 **250 次**，连续在涨 |
| 已接入的店铺 | 只有数字，36 分钟才跳一次 | **加 +N 浮起 + 副标「开幕以来 +N」** | 43 虚拟分钟：2,484 → 2,485，浮起 1 次 |

> 验这一条踩了个测试坑：三倍速跑 25 秒只等于 **1.25 虚拟分钟**，而订单是 55 秒一笔 ——
> 同一份代码两次跑，一次显示「动了」一次显示「没动」。要验低频事件必须把
> 采样窗口拉到远大于事件周期（这里用 20 倍速 × 30 秒 = 10 虚拟分钟）。

> **店铺这条要你知道**：引擎是 `NEW_STORES_PER_DAY: 40`，也就是**约 36 分钟才 +1 家**。
> 我没动这个数（它是产品数据口径）。现场大约每半小时能看到一次 +1。
> 要更频繁就得改引擎常量，那需要产品确认量级。

### 4. 右上角不能挂单个店铺的身份

这块屏上的订单来自全部接入店铺，写成「Riverstone 旗舰店」的话，
表里冒出别家店就自相矛盾了。改成平台方视角：

| | 改前 | 改后 |
|---|---|---|
| 侧栏 | AP 商家后台 / AI 渠道 | **AP 渠道运营台 / 全部接入店铺** |
| 右上角 | 卖 · Riverstone 旗舰店 | **运 · AP 运营 / 全部店铺 · 2,484 家**（数量实时） |
| 日志标题 | AI 正在读取**你的**商品页 | AI 正在读取的商品页 |

### 5. 一屏两个口径（顺手修的真 bug）

占比面板的基数原先写死用全量口径，于是顶栏选「开幕至今」时
**KPI 卡显示 44 万而饼图中心显示 4159 万** —— 同一屏两个口径，商家一定会问。
现在切换时间范围会重算占比基数（键不变，不重建 DOM），四张卡与饼图中心恒定一致。

日志行数因为地图区加高，从 8 行降到 7 行（速率不变，约 4.6 秒换一遍）。

## 第三轮改动（三条）

### 1. 大额成交改成全屏礼花庆祝

纸片跑在 canvas 里（不是 DOM）—— 200 多个 DOM 元素每帧改 transform 会掉帧，
也会破坏「DOM 节点恒定」这条自检。随机一律 `E.hash32`（规格红线：不许 `Math.random`）。

- 三处起爆：左下、右下各一炮打向中间，顶部再撒一层往下飘
- 纸片横向按 `cos` 压缩 → 翻面时会变窄，比纯旋转的方块像纸
- 中央玻璃卡：金额（104px）+ 店铺 + 国家·城市 + 哪个 AI 带来
- 停 4.2 秒自动收起；背景只压一层半透明幕，后台本身仍看得见（叠一层庆祝，不是切场）

**只给 epic / legendary 用**（约 15% 的订单 × 1.1 笔/分钟 ≈ 每 6 分钟一次）。
横幅留给里程碑 —— 每笔大单都全屏一次的话，3 分钟后就没人抬头了。

### 2. 店铺池换成真实客户报表（已脱敏）

来源 `AP展会\customers-report-2026-08-20.csv`，1075 家去重后 → **1035 家进池**。

| 处理 | 做法 |
|---|---|
| 店铺名 | **只留首尾几个字符，中间一律换成 `**`**（≤4 字→首1**尾1；5~8 字/中文→首2**尾2；9~14→首3**尾3；>14→首4**尾3） |
| 域名 | 用脱敏名现生成（`**` 转 `-`），不含任何原始信息 |
| Email / 联系人 / 安装时间 / 备注 | **一个字都没进交付物** |
| 地理不支持的国家 | 剔除（打不了地图点、取不到买家城市） |

`shops.js` 里每一行都带 `**`，扫过：无 `@`、无域名、无链接。屏上、抽屉里、导出的 CSV 里全是脱敏名。

**一个和「加入中文店铺」不太一样的发现**：报表里**中文店铺名只有 3 家**，另外 1072 家是拉丁字母名。
真正的差异在国家 ——

| | 真实报表 | 引擎原本的 18 个市场 |
|---|---|---|
| 前几名 | US 47.4% / GB 10.0% / **PK 9.9%** / FR 4.5% / AU 3.3% / **CN 2.6%** / **IN 2.5%** / **HK 2.0%** | US 34% / GB 9% / DE 9% / FR 6% / CA 6% … |
| CN / HK / TW / PK / IN | 合计 **17.6%** | **一个都没有** |

所以「中国跨境卖家的 Shopify 店名绝大多数是英文的」——这件事本身可能就是个有用的结论。
现在屏上会出现「中国 / 中国香港 / 巴基斯坦 / 印度」的店铺（国家列是中文），
但店名仍是报表里的（脱敏）英文名。**要额外造中文店名的话说一声，那就不是报表数据了。**

覆写做成一层 `applyShop()`，**没有改 `_shared/engine.js`** —— 那是 A/B/C/D 与 C-LED 共用的。
按 `store.id` 稳定映射（同一 id 永远同一家店），只覆写 name / domain / cc / 行业 / 买家城市，
**不覆写 currency 与 amount**：中国跨境卖家的店多半就是 USD 结算，保留引擎原值反而更真。
占比图基数与地图市场点也都改用真实分布，全屏口径一致。

### 3. 顾客来自哪里 → 可展开成全屏地球

地图卡右上角悬停出「全屏」按钮，或按 **`G`**；`Esc` 退出。

**渲染器直接用方案 B 的 `globe.js`**（真实城市点云 + 坠落的读取流 + 发射的订单弧线，
纯 Canvas 2D、零 WebGL、零 CDN）。本目录一份副本，**没碰 B 的那份**。相对 B 改了三处：

| 改动 | 为什么 |
|---|---|
| 球心/半径 `1470,556,486` → `960,452,352` | B 那一屏球在中央偏右；全屏要居中。现在直径 737px = 屏高 68%，与参考图接近 |
| 补了**大气光晕 / 球体本体 / 球缘亮边**三层 | B 的球是透明的（那一屏还有别的主角）。全屏时球本身是主角，得像个实体天体 |
| 加**真实海岸线层**（见下节） | B 只有城市点云，大陆是几撮孤立亮点。参考图的识别锚是连续、轮廓清晰的暗色大陆 |
| 城市点云改成**只落在陆地上**（见下节） | B 的卫星点在切平面上随机撒圆盘，不认陆地边界，沿海城市一半点掉海里 |
| 弧高大幅压低（见下节） | 全屏居中后，原版的高度会把弧线甩出屏幕 |
| 加 `focusLon()` **镜头跟随** | 见下 |

其余照 B 的原样：匀速自转 0.8°/秒、爬虫冷青、订单暖金、gradient 只在 `init` 建。

#### 大陆轮廓：Natural Earth 海岸线，不是点阵

第一版用平铺地图那套 **64×26 掩码**逐格画方块。那套只有约 700 个陆地格，
在直径 737px 的球上每格 30~50px —— **调过四版尺寸，每版都是方块拼贴**：

| 试法 | 结果 |
|---|---|
| 写死 7.4px | 一地分散的小点，看不出大陆 |
| 投影「经度 +1 格」取两点屏幕距离 | **球缘反而更大** —— 邻格已翻到背面，透视外推把距离算成大值 |
| 按 `P.z` 缩小球缘方块 | 球缘**还是**一整块 |
| 球缘淡出 | 不糊了，但大陆太淡、几乎看不出形状 |

**真因**：球缘处经度方向被透视压到极致，几十个格子挤在 20px 宽的屏幕区域里，
每个哪怕只有 9px 也连成实心块 —— **缩尺寸永远解决不了**。
而且点阵本质上做不出「轮廓清晰的边缘」，那需要多边形 `fill()` 的抗锯齿边界。

所以换成真实海岸线：**Natural Earth 1:110m「land」（公有领域）**，
取自 `world-atlas@2` 的 `land-110m.json`（TopoJSON）。
**构建时**解码 + Douglas-Peucker 简化（tol 0.34°）+ 丢弃 < 0.55 平方度的小岛，
落成 `coast.js`：**108 个环 / 2161 个顶点 / 29.6 KB**。
运行时只读这份扁平数组 —— 不引 topojson / d3-geo，现场断网照跑。

渲染两个要点：

- **包围球剔除**：每环预存中心向量 + `sin(角半径)`，每帧先变换中心那一个点，
  整环在背面就整环跳过。
- **跨球缘的环沿球缘弧闭合**：背面顶点按方位角贴到球缘就够了吗？不够 ——
  相邻两个背面点的方位角可能从 10° 跳到 350°，直线连接会**横穿整个球面**，
  球缘内侧糊出一堆尖角三角形（实测东亚/东南亚一带最明显）。
  所以连续的背面段要沿球缘**短弧插值**着走，大陆才会被球缘干净地切断。

108 个环拼进**一条** path 最后一次 `fill()` + 一次 `stroke()`（更亮的海岸线）。

#### 亮点必须贴在地图上，不能飘在地球上空

方案 B 的城市点云：每座城市在**切平面上撒一圈卫星点**（圆盘采样），
半径随人口权重走（最大约 6.6°）。它不认陆地边界 ——
所以圣保罗、布宜诺斯艾利斯这类沿海城市，**有一半点落到海里**，
那一簇看着就像「飘在地球上空」而不是贴在地图上。

修法是 GIS 里的标准两步：**rasterize + rejection sampling**。

1. **栅格化**：把 `coast.js` 的海岸线画进一张 1024×512 的等距柱状位图（约 0.35°/格）。
   跨 180° 经线的环（俄罗斯那条）在等距柱状上会从 x≈W 跳到 x≈0，直接 `fill` 会横穿整张图 ——
   所以画在**双倍宽**画布上、每个环画两遍（偏移 0 与 +W），最后取两半的**并集**：
   跨界的环总有一遍是连续的。
2. **膨胀 4px（≈0.7°）**：110m + DP 简化会削掉凹岸，有些沿海城市的坐标本身就落在
   掩码的海里（**实测悉尼就是**）。粗描边是最省事的膨胀，容差远小于要修的 20~40px 溢出。
3. **拒绝采样**：撒点时反算经纬度查掩码，落海就丢掉重采（配额 5 倍）。
   种子必须跟着**尝试次数**走，不是跟着已接受的个数 ——
   否则被拒的点会反复采到同一个位置，直接把配额耗光。

因为要补掉被拒的点，`cnt` 从 B 的 `22+w*13` 调成 `14+w*9`。

**实测**：球心区域取样 479 个白点像素，周围 6px 内找不到陆地的只有 **9 个 = 1.9%**
（改之前沿海城市大约一半在海上）。

> 验证这一条时踩了个测试坑：把大陆填充压暗一档后，溢出率「从 1.9% 涨到 5.6%」——
> 实际是**检测器**的阈值卡在陆地色 R≈38 的边界上，不是点跑到海里了。
> 阈值放宽到 28 就回到 1.9%。改了被测对象的外观，就要回头看检测器还成不成立。

#### 弧线要绕着地球飞，不能飞到宇宙外

方案 B 的爬虫是「从外太空 **1.6R** 坠落」，订单弧顶最高 **1.43R**。
那一屏球偏右、留白多，没问题；全屏居中后球心在 y=452、球缘投影半径 368 ——
1.6R 落在距球心 589px，**弧线顶端跑到 y=−137，也就是飞出屏幕了**。

| | 原版 | 现在 | 实测最高点 |
|---|---|---|---|
| 爬虫起点 `r0` | 1.58~1.72R | **1.09~1.14R** | — |
| 订单弧高 `h` | 0.13~0.43R | **0.04~0.15R** | — |
| 合计最远 | — | — | **1.15R（425px），顶端 y≈27，触屏边像素 0** |

验证方式：扫整张 canvas 找弧线颜色的最大半径，按通道区分弧线（G 或 R 最大）
与大气光晕（B 最大）。

全屏这一屏刻意**不跟随明/浅主题** —— 发光的天体只在深底上成立，白底上做「大气光晕」自相矛盾。

**镜头跟随**：订单来了把买家那条经线摇到正面（`easeInOutCubic` 1.3 秒），转完交回匀速自转。
不做这件事的话，自转只有 0.8°/秒、订单卡活 5.2 秒 → 转过来才 4.2° ——
**约一半的订单卡钉在球背面，永远看不见**（实测那一版 4 笔里只有 2 笔可见，改后 4/4）。
代入投影可得 `zr = cos(lat)·cos(lon+rot)`，所以正对镜头就是 `rot = -lon`。

**订单悬浮卡**用 `APGlobe.screenOf(lat,lon)` 钉在买家城市的球面点上，每帧跟着球转；
点转到背面就隐形。4 张预建循环复用（动态 append 会破坏 DOM 恒定）。

**底部跑马灯**每条 AI 读取记录从右往左飘。入队有闸门：队尾还远在屏外就先不加 ——
入队 3 条/秒（每条约 300px = 900px/s）而滚动只有 115px/s，不设闸门队列会无限堆积
（实测位移飙到 2600px，屏上只剩零星一条，看着像空的）。

## 第四轮改动（三条）

### 1. 球面亮点从"悬在上空"变成"贴在地表"

原来的撒点是在城市所在的**切平面上撒一个圆盘**，再投影回球面 ——
这个做法完全不看陆地边界，所以巴西东南、阿根廷那一带的点群直接糊到海里去了，
视觉上就成了"一层点飘在球的上方"，而不是"陆地表面亮起来的灯"。

改成 GIS 里的标准做法 **栅格化 + 拒绝采样**：

```
buildLandMask()   把 108 个海岸线环画进一张 1024×512 的等距柱状投影离屏画布
isLand(lat,lon)   查这张掩膜的单个像素
buildPoints()     每个城市撒 14 + round(权重×9) 个点，落到海里就重摇
```

三个细节是必须的：

- **反经线**（±180° 接缝）：环跨接缝时画在双倍宽画布上画两遍再取并集，
  不然接缝两侧会连出一条横贯地图的假陆地。
- **掩膜膨胀 4px**：110m 精度 + Douglas-Peucker 简化会把凹岸剪掉，
  悉尼实测被判成海。加一道粗描边把边界往外推 4px，再探 10/10 命中。
- **叠加混色 + 预渲染光斑**：`globalCompositeOperation='lighter'` 配一张
  径向渐变精灵，点密的地方自然堆亮 —— 这才是参考图里"城市灯光"的成因，
  单纯提亮每个点只会变成一片糊。

残留下海率 **1.9%**（改前是整片糊到海里）。

> 顺手记一条教训：改完陆地填充色之后，探针报的"下海率"从 1.9% 涨到 5.6%，
> 我以为是回归 —— 其实是我探针里 `c[0] >= 38` 这个阈值正好压在新陆地色
> `R≈38` 上。**改了被测对象的外观，探针就失效了**，得先校探针再读数。

### 2. 所有展示信息随机化（消除循环感）

点名的是"AI 爬虫亮点一直在循环"，但查下来循环感的真正来源是**内容池太小**：
商品名和 URL 路径都在少数几条上打转，看久了就发现是同一批在转。

新增 `feed.js` 作为内容层：

| 生成物 | 做法 |
|---|---|
| 商品名 | 10 个行业池 × 197 个品类词，每池绑定自己的**材质集**与**形容词集** |
| URL 路径 | 64% 商品页（带 variant / utm 参数）、18% 集合页（带分页 / 筛选 / 排序）、其余博客 / 页面 / 搜索 / sitemap / robots |
| 爬虫来源 | 14 个数据中心（权重 9）+ 42 个边缘节点（权重 2），坐标带 ±2.2° 抖动 |

接入方式和店铺层一样走**覆盖层** `applyFeed(o)`，三个调用点（订单入列 /
爬虫入列 / 历史预填），**一律排在 `applyShop` 之后** —— 商品名要按行业选池，
行业得先被真实店铺覆盖掉才是对的。

随机源全部走 `APEngine.hash32(种子)`，种子从订单号推导，所以**同一笔订单
反复渲染得到同一个商品名**（红线：不许用 `Math.random`，否则重绘就变脸）。

材质集当初是共用一份，结果冒出 `Cold-Brew Shampoo Bar`（咖啡词进了美妆池）
和 `Quilted Cleansing Oil`（纺织形容词修饰液体）。拆成 `food` / `care` 两套
材质 + 每池各自的形容词集才干净。

### 3. 左上角换成公司 logo

用的是 `AP展会\横排.svg`（595.3×186.1，比例 3.20:1）。

**不用 CSS filter，而是备两份文件**：

```
logo.svg       原图（深字，给浅色主题）
logo-dark.svg  把唯一一处 #040000 换成 #F2F5FA（浅字，给深色主题）
```

原因：`invert(1)` 会把图标那道**暖色渐变反成青蓝，品牌色就错了**。
而 `#040000` 在整个文件里只出现一次（就是文字色），换掉它文字变浅、
图标渐变**原样保留**。

切换靠 `#stage[data-theme]`，所以 `applyTheme` 里补了一句
`stage.setAttribute('data-theme', t.key)` —— **CSS 变量换不了图片**，
这是这次唯一必须动 JS 的地方。

全屏地球那一屏永远是深底，固定用浅字版，宽 168px，后面跟一条 1px 分隔线。

侧栏 `.brand` 高 57px（对齐顶栏），logo 宽 180px → 按 3.2:1 占高 56px，
侧栏 232px 减去左右各 18px 内边距还剩 16px 余量。

> 两个 svg 各 306KB（内嵌 8 张 base64 位图，Illustrator 导出的原样）。
> 只在首屏解码一次、不进渲染循环，所以不影响帧率；真要瘦身得重导出，
> 但那会动品牌资产，没自己动。

## 第五轮改动（十九条）

这一轮的主题是**「拟真」**：把所有「看着像后台但点了没反应」的地方补成真的，
并把两套主题贯彻到最后两个没跟上的地方（全屏地球、礼花弹窗）。

### 一、图表要真的在动

#### 1. KPI 趋势线：根因是画的量本身就是常量

原来 sk2（订单卡）推的是 `m.ordersPerMin`。翻引擎能看到

```js
function avgOrdersPerMin() { …只从 CONFIG 算，连时间参数都不收… }
```

**它是个常量**。常量序列过 min-max 归一化就是一条水平线 —— 这不是「不明显」，
是数学上不可能有起伏。sk1（商品页）推 `crawlsPerSec` 稍好，但 84 秒窗口内
只有百分之几的波动，看着也是平的。

第二个坑更隐蔽：量程有个「不小于均值 4%」的地板。改成推**累计量**之后，
本场累计读取页在开场就已经是 **806 万**（session 从开幕算起、boot 时预铺过历史），
31 秒窗口内的增量约 **1,169**，而 `mean × 4%` 是 **322,374** ——
地板比真实极差大 275 倍，于是任何累计量都被压成水平线（实测 y 恒等于 14）。

三处一起改：

| 改什么 | 改成 |
|---|---|
| 画什么量 | **累计量**（本场成交额 / 订单 / 读取页 / 店铺），单调递增 → 折线必然往右上走 |
| 量程 | 纯 min-max，**去掉均值地板**。只用相对 1e-6 兜住「完全恒定」（那是浮点噪声） |
| 重画节奏 | commit 每 900ms 落一点 + **每帧画**：committed 点整体按 frac 左移，头部连到实时值 |

实测线顶端 y 的极差从 **3px → 27px**，420ms（远小于 900ms 采样周期）内画面
变化 195~245 个像素 —— 也就是「逐帧在生长」而不是「每 3 秒闪一下」。

面积渐变（主题色 0.42 → 透明）是「看得更清楚」的主要手段：单根 1.5px 的线
在 96px 高的卡片右下角太轻，一片带色的面积才能在 1~3 米外被看见。
尺寸从 74×26 提到 **104×30**，并去掉了原来的 `opacity:.8`。

**成交额卡原先没有趋势线**（四张里只有它光着），补上了；反色卡上的线走
`fillTx`（浅字色）—— 用 `order` 的暖色压在 `#0B7360` 实底上对比度不够。

> 店铺数是**阶梯函数**（40 家/天 = 约 36 分钟才 +1），31 秒窗口内十有八九完全水平。
> 所以那条线画的是同一条公式的**未取整值**，也就是「正在累积的那一家」的进度：
> 引擎 `stores = STORES + floor(elapsedDays × NEW_STORES_PER_DAY)`，
> 这里去掉 `floor`。斜率用的是引擎自己的 `E.CONFIG.NEW_STORES_PER_DAY`，
> 不是我编的；与卡上那个整数最多差 1 家（开场的小数部分未知），只影响线的高度。

#### 2. 渠道分布卡从死卡片变成可交互

同一个面板里，右边的甜甜圈 hover / 联动都完整，左边五行占比条既不响应 hover
也不能点 —— 一屏两种交互约定，商家试过饼图之后必然会来点这边。现在对齐饼图：

- **hover** → 该行高亮、其余压暗，列头显示「渠道 · N 笔 · 占比」
- **点击** → 真的把订单表按这个渠道筛掉（等价于选 `fSrc`），再点取消
- **选中态**用左侧一道主题色竖条，鼠标移开也还看得见（只靠 hover 表示等于没有状态）

详情放列头而不是行内：行宽只有 74 + 条 + 44，塞不进第四个字段。

#### 3. 饼图中心的第三行压在扇区上

内半径 40 → 内圈直径只有 80px；在 y=102 那条线上的弦半宽是
`sqrt(40² − 23²) ≈ 32.7`，可用宽度只剩约 **65px**，而「6 个国家 / 地区」
11 个字符（CJK 约 10px/字）远超这个宽度。把它搬到列头（`#pieCC`），
内圈第三行留空给 hover 态显示该国金额 —— 两态仍是三行，切换不跳。

### 二、四张 KPI 卡都是指标选择器

原先只有第一张靠反色看着像被选中，其余三张点了毫无反应。现在四张都有选中态，
而且选中后做的事是**可预期且真的发生了**的：

| 卡 | 选中后 |
|---|---|
| 成交额 | 订单表改为**金额降序**（想看大单） |
| 订单 | 订单表回到**最新在前**（默认流态） |
| 读取 | 高亮下方「AI 正在读取的商品页」面板 |
| 店铺 | **跳到店铺页** —— 这个指标的明细在那，比在看板上高亮一个 36 分钟才 +1 的数字有用 |

选中的表达手段是**外描边 + 底部主题色横条**，不改背景色：第一张是反色实底，
靠背景表达选中的话它没有可用的第二种背景。再点一次取消。

### 三、四个内页补齐（原先是四个假入口）

侧栏「AI 订单 / AI 读取记录 / 店铺 / 设置」原先点了只换高亮，页面不变。
现在四页都是真的，代码在新文件 **`pages.js`**（app.js 已经 94KB，再塞 700 行没法看）。

三条设计约定，都是「真后台该有的样子」：

1. **分页表的自动刷新只在第 1 页开。** 订单/读取是活的流，翻到第 3 页还每秒重排
   的话行会在手底下跳走。真实后台的做法是第 1 页跟着流走、翻页即进入快照态
   **并明确告知**（分页条上那个「已暂停实时刷新（翻回第 1 页恢复）」）。
   不告知的话用户会以为数据断了。
2. **筛选 / 排序 / 搜索作用于整个缓冲，不是当前页。** 只筛当页是假筛选 ——
   第 2 页有匹配项却搜不出来。
3. **每页条数是按版面倒推的**，不是随手给的：
   统计条 62 + 表头 34 + 分页条 47 = 143 → 表体可用 832px，行高 34 → 24.4 行。
   给 24 行实测溢出 16px，所以三页统一 **23 行**（余 18px）。

|---|---|
| **AI 订单** | 6 项统计 + 搜索 + 三个筛选 + 清空 + 导出 + 9 列可排序表 + 分页 + 行点击出抽屉 |
| **AI 读取记录** | 5 项统计 + 搜索（路径/店铺/token）+ 两个筛选 + 8 列表 + 分页 + 导出 |

设置页排两列：单列排下来 1150px，在 1080 的屏上要滚 —— 而这是块朝外的展会屏，
没人会去发现设置页里还能滚。

> **订单页的统计条口径写得很啰嗦是故意的。** 这一页统计的是订单明细缓冲
> （最近约 80 笔，合计约 $1 万），而 KPI 卡上的成交额是本场累计（约 $50 万）。
> 两个数都对，但都叫「成交额」就是「一屏两个口径」——第二轮已经因为这个
> 踩过一次（KPI 44 万 / 饼图 4159 万）。所以标签写成「明细条数 / 这些订单合计 /
> 本场累计成交额」，并把两个口径并排放在同一条统计条上。

> **店铺页的逐店指标（SKU 数 / 近 7 日读取 / 累计 AI 订单 / 接入时长）是
> 按店名稳定推导的仿真值**，不是从 `ordBuf` 数出来的。理由：缓冲只有最近 80 笔订单，
> 1035 家店里 99% 会显示 0，那样的表比没有更糟。推导走 `APEngine.hash32(店名)`，
> 所以同一家店每次刷新都是同一组数字。设置页的「数据与口径」里如实写明了这一点。
> 读取量与 SKU 数正相关（页面越多被抓越多），已暂停的店读取量归零 ——
> 否则「已暂停」这个状态就没有意义。

改成「本页搜索在上方工具栏」。留一个点了没反应的搜索框，就是又一个假操作。

### 四、两套主题贯彻到最后两处

#### 1. 浅色主题下礼花弹窗还是黑的

根因很直接：`light` 主题**没有定义** `glassBg` / `glassBd` 这两个键，
而 `.cbox` 用的是 `var(--glassBg)` —— 于是它落回 `#stage` 行内的深色默认值。
两套都补齐后，浅色下是白卡 + 浅描边。

顺带补了 `celScrim`：礼花底下压一层**模糊幕布**。不加这层的话纸片和 104px
的金额全糊在后台的表格/地图纹理里，分不出前后景。blur 走单独一层而不是加在
`#celebrate` 上 —— canvas 是它的子节点，给父节点加 `backdrop-filter`
会把纸片自己也一起模糊掉。

礼花配色的最亮那一档也得分主题：**白色纸片在浅色幕布上直接消失**（实测截图里
有一批纸片是隐形的），浅色下换成中饱和的琥珀 `#E09A3C`。

#### 2. 全屏地球跟随主题

原来的判断是「这一屏刻意不跟随主题，发光天体只在深底上成立」。**那个理由只对了一半**：
浅色主题下整个后台是白的，按 G 突然全屏黑，比配色不统一更突兀。

所以浅色下换的是**隐喻**，不是把深色版调亮：

| | 深色 | 浅色 |
|---|---|---|
| 隐喻 | 夜地球，城市灯光在发光 | 白日卫星图 / 纸质地球仪 |
| 城市点 | 暖白，`globalCompositeOperation='lighter'` 累加 | **深墨点**，`source-over` |
| 大气 | 蓝色光晕 | 极淡的冷色雾（只用来把球和背景分开） |
| 球缘 | 受光侧**亮**边 | 上暗下更暗的**收**边 |
| 陆地 | 比海面**亮**一点 | 比海面**深**一档 |
| 星空 | 有 | 无（白日地球没有星星） |

**硬把夜地球调亮只会得到一团灰雾** —— 发光在白底上物理上不成立，
而城市点用 `lighter` 混合在白底上会越叠越白、直接消失。

canvas 侧的两套值收在 `globe.js` 的 `PAL`，`APGlobe.setTheme(key)` 重建
所有跟色值有关的 GPU 侧对象（4 个渐变 + 辉光精灵 + 12 档弧线样式）；
几何（点云 / 海岸线 / 经纬网 / 星位）与颜色无关，不重算。
DOM 侧（顶栏 / 四个指标 / 跑马灯 / 球面订单卡 / logo）走
`#stage[data-theme="light"]` 的一组覆写。

> 浅色球体最亮那一档不能太接近页面底色。第一版给到 `rgb(226,236,245)`，
> 压在 `#FFFFFF` 背景上时球的左上角整片糊进背景里（实测截图）。
> 现在最亮处也比背景暗约 40 个亮度单位，整圈边界都立得住。

#### 3. 星空（只在深色）

深色下球外面原本是一整片纯黑 —— 那是「什么都没有」，不是太空。
星点要满足两件事才像真的：**分布不均匀**（真实星野是成团的）、
**亮度分档且缓慢闪烁**。均匀撒 + 同亮度 = 一张噪点贴图。

620 个点，用一层低频噪声当接受概率做成团分布，球体+光晕罩住的范围内不撒
（星星画在球面上就成了噪点）。三档亮度：绝大多数是暗的小点，少数几颗亮星。
每帧只改 alpha（0.55 rad/s 的闪烁），位置一次算好存 `Float32Array`。
随机走 `E.hash32`，所以每次刷新星图完全一致。

#### 4. 大额庆祝现在盖得住全屏地球

`#celebrate` 的 z-index 是 **80**，而 `#gv` 是 **85** —— 地球开着的时候礼花
整个被地球盖住，等于「全屏地球里不庆祝」。改成 95。纸片与弹窗都在，
幕布的 blur 把地球也一起虚化，前后景分得开。

## 扫码全链路（第六轮补的）

原来这一条的验收结论只有一句「矩阵与参考实现逐格一致」。**那句话的证明力比看起来弱得多**：
它只说明我的编码器和另一份实现算出了同样的矩阵；如果两边对掩码、纠错块交织、
格式信息 BCH 的理解**一样错**，就会一起错，而扫描器读不出来。
换句话说，**在此之前从来没有任何解码器读过这个二维码一次。**

现在按「手机扫不到的四类真实原因」逐条闭环，脚本是 `_checks/ckQr.js`：

| 会出什么问题 | 怎么验的 | 结果 |
|---|---|---|
| ① 码本身编错 | 两个**血统不同**的解码器：OpenCV `QRCodeDetector`（自研）+ ZBar（手机 App 里大量在用的老 C 库）。canvas 原图、屏上尺寸、深浅两主题的整卡截图共 4 张，各读一遍 | 8/8 都解出正确 URL |
| ② 屏上太小 / 拍糊 | 按真实显示尺寸做退化：缩放 × 高斯糊 × JPEG 压 × 旋转 | 180px 下三档全解；120px 仍 3/3；约 96px 才开始失败 |
| ③ 码里的地址错 | 断言地址非 localhost、来自实时探测、HTTP 可达且返回的确实是问卷页 | 通过 |
| ④ 打开了但用不了 | iPhone 13 视口真的走完问卷：4 题（身份题 + 分支题 + 必填联系方式）→ 转盘 → 中奖 | 通过，并顺带验到必填校验会拦空 |

尺寸账：v3 = 29×29 模块，加 4 模块静默区共 37；canvas 333px，屏上显示 180px
→ **每模块 4.86px**（屏幕扫码的通行下限是 4px，有余量但不多）。

> **仍然没做的**：拿真手机、在真展会屏前、隔着真实距离扫一次。
> 上面的退化测试是它的**代理**而不是替代 —— 真手机还牵扯屏幕反光、
> 自动曝光、摄像头畸变这些我模拟不了的东西。这一步需要人，留着。

### 顺手修掉的一个「屏上一切正常但打不开」的坑

`surveyUrl()` 原来的逻辑：`location.hostname` 不是 localhost 时用它，否则退回
`SURVEY_FALLBACK`（一个写死的 IP）。问题是**现场操作员几乎一定开 localhost**，
所以真正生效的永远是那个写死的地址 —— 而它是 **DHCP 分配**的
（实测 `192.168.56.67` 确实是本机 WLAN 的当前地址，但换网络、甚至同网络重新租约就变）。

后果不是"码扫不出来"，而是**"码扫得出来、打开是个连不上的页面"**，
而屏上一切正常，最难发现。

改法：`_serve.js` 加了 `/__lan`，用 UDP connect（连公网地址但**不发包**，
让操作系统按路由表选出口网卡）报告本机真实 LAN IP，页面拿到后重画二维码。
比遍历 `os.networkInterfaces()` 猜可靠得多 —— 本机同时有 4 个 `169.254` 链路本地、
1 个 Tailscale `100.65`、1 个真实 WLAN `192.168`，靠名字或顺序猜必然猜错。

`APDiag_qr.src` 会如实记录地址来源：`lan:<ip>`（探测到且换了）/
`lan-confirmed:<ip>`（探测到且与兜底一致）/ `fallback`（**探测失败，在赌写死的 IP**）。
> 这个字段第一版只在"地址变了"的分支里写，于是兜底 IP 恰好等于真实地址时，
> 分不清「探测成功」和「探测根本没跑」—— 而这恰恰是最需要知道的一件事。

## 引擎事实（踩过才知道的）

1. **`APEngine.dt()` 返回毫秒**（就是 `_dtMs`），不是秒。按秒再乘 1000 会让每帧虚拟推进 16.7 秒。
2. **`triggerOrder` 收的是 `{usd}` 对象**，不是位置参数。传位置参数会退回引擎的
   `forceBig` —— 那条路中位数只有约 $310 而 epic 门槛正好 $300，于是「B 键一半时间不出大单」。
3. **`peekOrders(n)` 有 62 笔硬上限**：传 200 / 600 / 1500 / 4000 得到的都是同一批。
4. **`platformBreakdown()` 是权威渠道占比**，别再用 `peekOrders` 取样估。
5. **`APGeo.CITIES` 是数组的数组** `[名称, 纬度, 经度, 国家码, 权重]`，按对象属性取 `cc` 全落空。
6. **`APGeo.MARKETS` 有 18 个市场**（含 `AE` / `DK`）。`CC_CN` 少一个，
   筛选下拉里就会冒出一个光秃秃的 `AE`（实测踩到）。

## 这一版自己踩的坑

1. **split-flap 的空格格会被 HTML 折叠**。每格是独立 `inline-block`，
   一个格里只放一个空格时会被吞，时间显示成 `08-2010:45:18`。修法是 `.cf span{white-space:pre}`。
2. **时间列 108px 装不下 14 字符**：Consolas 13px 字宽约 7.15px × 14 = 100px + 24 内边距 = 124。
   给 108 会被裁 9px。现在 128。
3. **两个 136px 的独立面板装不下「头 42 + 5 行」**，Perplexity 和「其他」被挤掉（实测只显示到第 3 行）。
   改成一个面板两列后每列有 246px 可用。
4. **日志行高 25 时第 8 行超出可用高度 1px**（275 − 42 − 32 − 2 = 199 < 200），改 24。
5. **浅色下 `#B4E8DC` 的占比条等于没有**，6% 那条直接消失。改 `#5FC9AF`。
6. **实底徽标的字色必须走 `--tx`**：`.tag.t3` 原先是 `--order` 压在 `--order-d` 上，
   浅色下对比度只有 2.3:1，糊成一团。
7. **又踩了「带反引号的长文本别走 bash」**：写验收脚本时 heredoc 报
   `unexpected EOF while looking for matching '`。长文本一律用 Write 工具。
8. **甜甜圈的 hover 不能用 `page.hover(选择器)` 测**：Playwright 取元素 bbox 中心，
   而环形扇区的 bbox 中心常常落在甜甜圈的洞里，于是报「svg intercepts pointer events」。
   要按角平分线算一个真正落在扇区内的点（`APDiag.pieItems` 暴露了起止角就是为了这个）。
9. **甜甜圈中心的文字会溢出内圈**：内半径 40 → 内圈直径只有 80px，
   「美国 · $156,969」挤成一行会甩到图外。拆成固定三行。
10. **验低频事件必须把采样窗口拉到远大于事件周期**：三倍速跑 25 秒只等于
    1.25 虚拟分钟，而订单是 55 秒一笔 —— 同一份代码两次跑，一次「动了」一次「没动」。
    改用 20 倍速 × 30 秒（10 虚拟分钟）才测准。
11. **球面大陆用点阵是条死路，调了四版才认**（详见上文「大陆轮廓」一节）。
    结论：**点阵做不出清晰边缘**，要清晰轮廓只能多边形 `fill()`。
    这一条上浪费的时间最多，起因是「先想怎么把手上的数据用好」而不是
    「这个效果需要什么数据」—— 后者才该是第一个问题。
12. **逐点设 `globalAlpha` 会把 fps 从 60 打到 46**。批量绘制要预分配
    `Float32Array` 缓冲、按档分批，把 `fillStyle` / `globalAlpha` 的设置次数
    压到个位数。
13. **背面顶点不能只按方位角贴球缘**：相邻两点方位角跳变时直线会横穿球面，
    球缘内侧糊出尖角三角形。必须沿球缘短弧插值。
14. **别自己手搓地理数据**。我先手写了一份约 480 顶点的简化海岸线，
    然后才去查有没有成熟数据 —— `world-atlas` 的 Natural Earth 110m
    一条 `curl` 就拿到了（55KB），而且是公有领域、精度高一个量级。
    **顺序应该是先查现成的，再考虑自己造。**
15. **改了被测对象的外观，探针就失效了**。把陆地填充调暗之后，"点下海率"
    从 1.9% 跳到 5.6% —— 不是回归，是我探针里 `c[0] >= 38` 的阈值正好
    压在新陆地色 `R≈38` 上。读数之前先校探针。
16. **在动的东西上按固定屏幕坐标取样，等于抛硬币**。"大陆填充在画"这条
    断言扫 5 条纬线数陆地色像素，阈值写 `>60`；实测同一份代码在太平洋面
    只有 **17** 点、在欧非面有 **147** 点，中位数正好 60。改成先
    `APGlobe.focusLon()` 钉住经度再取样 —— 钉住之后还能顺手把断言变强：
    不再问"有没有亮"，而是问**亮的分布像不像真实海陆**（欧非面 109 vs 太平洋面 17）。
17. **JS 块注释里别写 `**/`**。我在注释里写"**216 种**/语言"，那个
    `**/` 直接把注释闭合了，报 SyntaxError。五个 js 文件都扫过一遍。

18. **通用类名 + `opacity:0` 是个陷阱。** `.act` 原本是订单行里 hover 才显形的
    「查看」，是个**全局**选择器。后来「暂停滚动」按钮按下时也加 `act`，
    于是整个按钮 `opacity:0` 变透明 —— 用户报的是「按钮点了就看不清」，
    根因却在一个完全无关的组件上。**表示状态的类名要么带组件前缀，要么把选择器限定到容器内。**

19. **「趋势线不明显」有可能根本不是显示问题。** 先去看画的是什么量：
    `ordersPerMin` 连时间参数都不收，是常量 —— 常量归一化后必然是水平线。
    调线宽、调颜色、调 alpha 全都是白费。**先问「这个量会变吗」，再问「画得清不清楚」。**

20. **归一化的「保护性地板」会在大基数上反噬。** 「量程不小于均值 4%」本意是
    防止把微小波动放大成陡坡，但累计量的基数是 806 万、窗口内增量只有 1,169，
    地板比真实极差大 **275 倍**，把所有曲线压成了直线。
    **凡是「不小于均值 x%」这类相对地板，都要拿真实基数和真实增量算一遍比值。**

21. **主题变量漏一个键，症状会出现在毫不相干的地方。** `light` 少了
    `glassBg`/`glassBd`，表现是「浅色主题下礼花弹窗还是黑的」——
    因为 `var()` 会静默落回 `#stage` 行内的深色默认值，**不报错、不告警**。
    加主题时应该拿两套的 key 集合做一次差集，而不是靠肉眼扫。

22. **z-index 要按「谁能盖住谁」列一遍，不能各自拍。**
    `#celebrate` 80 < `#gv` 85，于是「全屏地球里不庆祝」——
    两个功能各自都对，组合起来才错。现在的层序：
    抽屉 70 < 礼花幕布/纸片 95 > 全屏地球 85 > 横幅 50。

23. **浅色主题不是把深色调亮，是换隐喻。** 夜地球的城市灯光靠
    `globalCompositeOperation='lighter'` 累加，白底上用它只会越叠越白、点全消失。
    浅色下必须换成「白日卫星图 + 深墨点 + `source-over`」，
    连「陆地比海面亮」都要反过来变成「陆地比海面深」。

24. **别把「多字段搜索」当成「按某一列搜索」来断言。** 验收脚本搜「Gemini」
    断言每一行的 bot 列都含 Gemini，结果失败 —— 因为 `feed.js` 会生成
    `?utm_source=gemini` 的路径，那些行命中的是**路径**，行为完全正确。
    是探针错了不是产品错了。**多字段搜索的断言要用 `some` 不是 `every`。**

25. **分页表的行数要按可用高度倒推，并留一行余量。**
    统计条 + 表头 + 分页条 = 143px 是固定开销，剩 832px / 34px = 24.4 行，
    给 24 行实测溢出 16px（统计条项数不同会差几个像素），给 23 行才稳。

26. **「与参考实现逐格一致」不等于「能用」。** 二维码这条验收挂了好几轮，就因为
    对照的是另一个**编码器**而不是**解码器** —— 两边对同一条规则理解得一样错就会一起错。
    **凡是"我的实现和另一份实现结果相同"这种论证，都要问一句：有没有独立的消费方读过它？**

27. **截图之前先确认元素是可见的。** `ckQr.js` 第一版忘了按 Q 展开二维码卡，
    而收起态是 `opacity:0` + `scale(.98)` —— 截到的是个不可见还被缩过的元素，
    两个解码器都读不出来，三条断言全红，差点当成产品缺陷。
    `locator.screenshot()` **不会**因为元素不可见而报错，它照样给你一张图。

28. **诊断字段只在"异常分支"里写，就分不清"正常"和"没跑"。**
    `APDiag_qr.src` 原来只在探测到的地址与兜底不同时才写，
    而兜底 IP 恰好等于当前真实地址 —— 于是显示 `fallback`，
    完全看不出探测到底成功了没有。而"到底在不在赌那个写死的 IP"正是唯一想知道的事。
    **状态字段要在所有分支里都写。**

29. **改了外观，先重新校准依赖外观的断言。** 「趋势线有面积填充」这条断言的阈值是 6px，
    而去掉量程地板之后，它量的那个值期望正好是 7px —— 阈值压在期望值上就是掷硬币。
    **动了渲染，就要把所有量像素的断言拿实测数据重新对一遍**，不能只看它还是绿的。
    校准要留证据：现在 `ckSpark.js` 里写着「12 次采样实测 3.4~7.1」，
    下一个人想把阈值调回去之前，会先看到这个区间。

30. **断言不要替数据做保证。** 三次红都是这个病：
    「筛 200 一定会减少行数」（缓冲区可能全是 200）、
    「搜 Google-Agent 一定有结果」（该 token 只占 2.4%）、
    「清空后行数等于初始全集」（缓冲区是活的，筛选那几秒里它自己还在长）。
    正确的做法是**只断言恒真的性质**（筛完不会变多 / 清空后不少于初始且严格多于筛后），
    数据相关的部分要么轮询到出现、要么明说「本轮数据退化，不算验过」——
    **不确定的事情就别判失败，但也别假装验过了。**

31. **共用一个 DOM 节点的多种状态，读之前必须掐掉别的来源。** 横幅只有一个节点，
    大额成交和平台里程碑轮着占用它。3× 速度下自然里程碑会把自己造的那笔顶掉，
    于是「两类配色不同」偶发读到两个里程碑色。**降速 + 等类名真的到位再读**，
    别用 `waitForTimeout` 赌时序 —— 这和上一轮「3× 下自然订单污染 lastOrder」是同一个病。

32. **断言要盯不变量，不要盯某一种实现。** `ckQr.js` 里「联系方式留空会被拦住」
    这条，写的是「点一下『下一题』要弹出错误文案」。后来把拦法从「点了报错」
    换成「按钮直接禁用」——**保护变强了，断言却红了**，差点当成产品缺陷。
    改成断言真正的不变量：*空着的时候前进不了*（禁用或报错都算，只要还停在同一题）。
    同一个病的另一面：只断言「首屏看不到奖品」，那么把奖品从产品里整个删掉也会通过 ——
    必须同时断言「转盘页四格还在」，才区分得出「延后展示」和「删了」。

33. **验「取消了自动跳转」要等得比原来的延时长。** 旧行为是 `setTimeout(next, 180)`。
    如果只等 200ms 就断言「还在原题」，通过与否基本靠运气。这里等 **1200ms**。
    另外要**正向**再验一次「点了『下一题』确实会走」—— 否则把 `next()` 整个删掉也能过。

34. **「localStorage 里有东西」不能当成「落库了」。** 上一版 `ckQr.js` 就停在这一步，
    还打了个 OK；而当时的真实情况恰恰是「服务端一条记录都没有」。
    要从**消费方**（服务端 `/api/survey/list`）把它读回来、逐字段比对，才算验过。
    这和二维码那条是同一个教训：**有没有独立的消费方读过它？**

35. **帧率断言必须带对照组，否则分不清「产品退化」和「机器忙」。**
    这一轮 `ckFinal.js` 的「全屏地球 rAF > 50」红了（46.6 / 48.9），
    但同一次控制实验里 `about:blank` 24.7（README 记的天花板 24.5）、
    平铺视图 60.3（基线 60）—— 基础帧率通道没变，只有地球这条在 **46.6~57.8** 之间摆。
    阈值 50 正好压在摆幅中间 = 掷硬币。诊断脚本 `_checks/_fpsControl.js`
    一次量三个（blank / 平铺 / 地球）并给出地球÷平铺的比值，这个比值不受机器负载影响。

**这批套件本身修过一轮 flake。** 连跑 3 遍 ×7 套件全绿之前，`ckSpark` 和 `ckReal`
会**随机**红 —— 三处成因各不相同，但都是**断言在替数据/时序做保证**：

| 症状 | 真因 | 现在怎么写 |
|---|---|---|
| `sk0/sk2 平均列高 4.0~4.3px` 偶发红 | 阈值 6 正好压在期望值 7 上（渐变按画布铺，alpha>24 只探到 y≈22；折线占满框高后平均线顶 y≈15） | 换成两条不随相位漂的：alpha>0 跨度 ≥5，且上段/下段 alpha ≥3 倍 |
| `筛选「200」→ 行数变了（120 → 120）` | 爬虫状态绝大多数是 200，缓冲区里没有非 200 行时**不变才是对的** | 先验恒真性质（不会变多），再遍历 option 找真有区分度的；全退化就明说不算验过 |
| `两类提醒配色不同（都是 rgb(0,211,167)）` | 横幅只有一个 DOM 节点，3× 速度下**自然**里程碑把自己造的成交顶掉了 | 降速 0.1 掐掉自然事件 + `waitForFunction` 等类名到位再读，不盲等 |

flake 顺手带出一个**真缺陷**：**「清空筛选」只清了一半。**
三个内页的清空按钮都只重置了内部状态 `S.*.f` 和搜索框，**从没碰过 8 个 `<select>`** ——
点完清空，表格确实回到全集了，可下拉框还停在「200」上。
界面显示着一个并没有生效的筛选条件，操作员看到的和数据实际的对不上，
这比不给这个按钮更糟。修法是 `pages.js:resetInputs()`，用 `selectedIndex = 0`
（不依赖第一个 option 的 value 怎么写）。

上一轮「假操作全局盘查」判的是「点了有没有状态变化」—— 清空筛选**有**变化，所以过了。
这次多问一句「**控件自己回位了吗**」才抓到。
**「有反应」和「反应是对的」是两条断言**，别用前者冒充后者。

这也是修 flake 值得做的原因：一个随机红的断言会被当成噪声，
它身边真正的红也就一起被忽略了。
