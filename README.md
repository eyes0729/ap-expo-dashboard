# AP 展会大屏与声音播报 · 四方案原型

四个可本地预览的大屏原型。同一套数据引擎和音效引擎，四种呈现方式，用于选型评审。

---

## 怎么预览

**必须**双击根目录的 `启动预览.bat` → 自动开 `http://localhost:8099/`。
这条路也最接近展会现场的真实部署方式（现场也是本地服务器 + Chrome kiosk）。

> ### ⚠ 不要双击 `index.html`
>
> 早期版本说过「直接双击 index.html 也行」，**那条建议现在是错的**，而且
> 错得不明显 —— 页面照常显示、数字照常涨，但两个东西会静默失效：
>
> | 双击 `index.html`（`file://`） | 后果 |
> |---|---|
> | 拿不到 `/__lan` | 二维码停在代码里**写死的兜底 IP**。码画得很漂亮、能扫出内容，但打开是个连不上的页面 |
> | `fetch` 被 CORS 拦死 | **人声包加载失败，播报退回系统旧音色**（Huihui） |
>
> 这就是「扫码还是打不开」最常见的原因 —— 实际就踩到过一次。
> 现在屏上会**明确报出来**：二维码被打上灰色「扫不开」，下面一条红色告警
> 写清原因和改法（见 `app.js` 的 `showBad()`）。看到那条告警就是这个问题，
> 关掉窗口改用 `启动预览.bat`。
>
> 数据引擎、视觉、快捷键在 `file://` 下仍然完全可用 —— 只看画面效果时
> 双击没问题。**但凡要扫码或听人声，就必须走 `启动预览.bat`。**

### 改 `.bat` 的人先读这条：必须保持纯 ASCII

三个启动器里**一个中文字都不能有**，中文提示全部由 `_serve.js` 打印。

不是风格问题。`chcp 65001` 之下 cmd.exe **按字节推进、按字符解析**，中文会让两者
错位；一旦错位越过读缓冲边界，cmd 就开始把文件**后半部分的片段当命令执行**：

```
'浏览器由' is not recognized as an internal or external command
'二维码和人声在服务停止后都会失效。' is not recognized as an internal or external command
```

被毁的是**文件尾部**，而 `pause` 就在尾部 —— 于是**窗口闪一下就关，还看不到任何报错**。
这个坑真踩过：启动器加了中文横幅、涨到 27 行就触发了；原来 6 行的版本不会，
因为漂移还没累积到边界。短文件测不出来，**必须整文件跑一遍才算验过**。

项目里 `make-voice.ps1` 早就为 `.ps1` 立过同一条规矩（中文放 `lines.json` 里读）。
`.bat` 同理。另外 `.bat` 必须是 **CRLF** 换行。

进去以后**先点一下屏幕** —— 浏览器规定音频必须由一次用户手势解锁，这不是 bug。

### 必按的几个键

| 键 | 作用 | 为什么重要 |
|---|---|---|
| `B` | 人工触发一个大单 | **最重要的一个键**。BD 讲到关键处按一下，屏上跳出一笔大额订单配合话术，这是全场最有效的演示动作 |
| `3` | 三倍速 | 彩排用。10 分钟的节奏压成 3 分钟看完 |
| `空格` | 暂停 / 继续 | 给人看清某一帧 |
| `M` | 静音 | 邻摊投诉时的第一反应 |
| `K` | 里程碑庆祝 | 看全屏庆祝的效果 |
| `G` | 调试网格 | 到场校准关键数字有没有压在 LED 拼缝上 |
| `H` | 展馆音频模式 | 切掉 100Hz 以下 + 补人声频段。**笔记本上别开**，会听不到大单的低频 |
| `?` | 全部快捷键 | — |

| | 日增页面 | 102,400 | 40 新店 × 320 × 8 |

| | 日订单 | 1,520 单 | **理论 1,489，事件生成器实测 1,520，差 2%** |
| | 客单价 | 中位 $74 / 均值 $139 | 对数正态 + 有硬顶的帕累托尾 |
| | 日 GMV | ≈ $211,000 | — |

**需要产品确认的就三个数**：表里带 ★ 的两个基线 + `PAGES0`。它们是对外口径，
都不能超过公司对外最大公开数字 × 1.2，否则是自打嘴巴。要改就改
`_shared/engine.js` 顶部的 `CONFIG`，三个数字会自动一起变、自动保持自洽。

展会当天的实际观感（09:00 开幕 → 18:00 收摊）：
`爬虫访问 420,000,000 → 421,207,397`（+40/秒，末两三位一直在滚）、
`AP 页面 6,144,000 → 6,187,445`、`AI 引荐订单 296,000 → 296,575`。

### 节奏是设计出来的，不是靠运气

- 每 **90 秒**保底 1 单（时间槽 + 洗牌袋），所以**不会冷场**
- 每 **10 分钟**一次 3~5 单齐发的大高潮，且第一单强制走大额
- 实测订单间隔：中位 **57 秒**、p90 **100 秒**、最长 **117 秒**
- 人声播报约每 **2.4 分钟**一次（只有 `rare` 及以上才播，`common` 只给一声轻提示）

### 断电了也不怕

所有计数器是**时间的纯函数** —— 从固定开幕时刻积分到当前时间，不存任何状态。
重启后自动对上，永不倒退、永不归零。第二天开机接着第一天涨（夜间降速到 15%，
完全冻结反而会立刻暴露是脚本）。

## 相比领导最初的想法，改了四处

拿去汇报的时候可以直接用这四条。

| 原想法 | 问题 | 改成 |
|---|---|---|
| 三个数字都做成巨型上涨数字 | 三个一样大 = 没有主角，冲击力被自己稀释 | 只留一个绝对主角（AI 爬虫访问量，它增长最快、最像心跳），另两个降为配角 |
| 每笔订单都播报 | ① 展馆有 85dB 强制上限，10 英尺内测量、投诉可执法关摊 ② 播报太密观众会自动屏蔽，中奖感归零 | 只有大单出人声（约每 2.4 分钟一次），小单只给一声轻提示。稀缺才有价值 |
| 「XX 店铺收获 **GPT 订单** $128」 | OpenAI 开发者条款明文禁止任何可能让人以为与其合作/被其背书的**表述和设计选择**，也禁止其 logo 用于展会物料 | 「XX 店铺收获一笔**来自 AI 助手的订单** $128」/ `AI-referred order`。冲击力一点不少 |
| 靠巨型数字本身产生冲击 | 数字没有参照系就是视觉噪音 —— "8,412,367 页"到底是多是少？ | 加"距下一个里程碑还差多少"的进度条 + 换算行（`≈ 每 27 秒新增一页`），并挂 Adobe / Shopify 的公开数据做外部对照 |

另外补了一条领导没提但更值钱的：**方案 D 把这块屏和现场已定稿的问卷抽奖活动打通**，
让路过者能变成销售线索 —— 展会唯一有效的 KPI 是留下线索，光有大数字留不下。

## 扫码：为什么以前「换 5G 换 WiFi 都扫不出」，以及怎么修的

**先排除掉一个嫌疑：码本身是对的。** `qr.js` 是手写的编码器，所以先拿一个独立解码库
（jsQR）做了 6 例往返，全过；`_checks/ckQr.js` 里还有 OpenCV + ZBar 两个独立解码器
在真实渲染上读它，也全过。编码没问题。

**真正的原因是码里装的地址。** 以前二维码里是
`http://192.168.56.67:8099/E-survey/` —— 一个 RFC1918 **私网地址**：

| 手机的网络 | 结果 | 为什么 |
|---|---|---|
| 5G / 4G | **必然失败** | 私网地址在公网上不路由，运营商网络里没有这台机器。这跟信号好不好无关，是物理上不可达 |
| 另一个 WiFi | 失败 | 不同网段 |
| 同一个 WiFi，但开了客户端隔离 | 失败 | **展会 / 酒店 / 机场 WiFi 默认就开这个**，同网段设备之间互相不通 |
| 同一个 WiFi 且没开隔离 | 能通 | 也就是「在办公室测好好的，到现场就废了」 |

所以现场表现是「同事换 5G 也不行、换 WiFi 也不行」—— 这不是偶发问题，是必然。

### ⚠ 先看这条：隧道方案在国内不成立，已改回局域网为默认

一开始的修法是起一条 cloudflared 公网隧道，二维码装
`https://<随机>.trycloudflare.com/s`。**这个方案在国内手机上不成立** ——
实机扫码得到「网络出错」。

**而这个结论被我自己的测试掩盖了很久，这才是最该记下来的部分：**

本机 DNS 被网关（`192.168.56.2` / `op.lan`）整体劫持 ——
`trycloudflare.com` 解析出来是 `198.18.84.62`，那是 **Clash 这类透明代理的
fake-IP 默认网段（198.18.0.0/15）**，不是真的 Cloudflare 地址。
于是笔记本上 `curl` 一路 200，**因为流量走了代理**；手机 5G 没有代理，必然失败。
连显式指定阿里 DNS（`223.5.5.5`）查回来的也是同一个 fake IP，说明 53 端口也被劫持。

> **通用教训：在被劫持 / 走代理的网络里，本机 `curl` 不能当作
> 「手机能不能访问」的证据。** 这类环境会让每一条可达性断言都变成假阳性，
> 而假阳性比没有测试更危险 —— 我据此说过「实测公网可达」，那是错的。

所以现在：**默认不开隧道，二维码里是局域网地址。**

| | 地址 | 字节 | 二维码 | 每模块 | 手机 5G |
|---|---|---|---|---|---|
| **默认（局域网）** | `http://192.168.x.x:8099/s` | 27 | **v3** 29×29 | **4.86px** | ✗ 需同网 |
| 隧道（`启动预览-公网隧道.bat`） | `https://<随机>.trycloudflare.com/s` | 51~69 | v5 37×37 | 4.00px | ✗ 国内打不开 |

局域网地址短得多，**二维码反而好扫一档**。

**现场怎么办：带一个随身路由器**，笔记本和观众手机都连它，关掉客户端隔离。
零外网依赖，最抗故障。代价是观众要先连 WiFi 才能扫，会掉一些转化率。

要一个真正「手机 5G 直接能扫」的地址，只有把问卷页放到**国内可访问的主机**上
（自有域名 + 国内云），那需要账号权限，我做不了。

以下保留隧道方案的实现说明 —— 它仍然可用（`启动预览-公网隧道.bat`），
在能真正访问 Cloudflare 的网络里是有价值的。

**实现：`_serve.js` 起一条 cloudflared 公网隧道**，二维码改成装 `https://<随机>.trycloudflare.com/s`。

- 隧道**默认不开**。要开：双击 `启动预览-公网隧道.bat`（或 `--tunnel` / `AP_TUNNEL=1`）
- 就绪前二维码先显示局域网地址，就绪后（约 10~30 秒）**自动重画**
- 隧道断了会自动重连；重连会换域名，所以屏幕每 20 秒问一次 `/__lan`，变了就重画
- 默认就是关的；开了之后 `_serve.js` 会自己拉起 cloudflared 并自动重连
- 协议锁了 `http2`（走 TCP 443）。默认的 quic 要 UDP 7844，很多网络直接丢包
- `/s` 是短链（302 → `/E-survey/`）。纯粹为了**好扫**：字节数少 8 个，
  二维码从 v5(37×37) 降到 v4(33×33)，同样尺寸下每个模块大 12%

### 顺手堵掉的一个数据泄露口（这条比扫码本身更要紧）

加隧道会**静默**开出一个洞，而且屏上一切正常：

cloudflared 跑在本机、回源到 `127.0.0.1`，所以隧道进来的请求 `socket.remoteAddress`
是 `::1` —— 和操作员开 localhost **完全一样**。原来的 `isLocal()` 只看 IP，
于是整个公网都被判成本机。**实测过一次：`/api/survey/export` 从公网直接返回
200 + 全量 CSV，里面是参与者的微信号和手机号。** 而二维码就印在一块所有人都会拍照的大屏上。

修法是 fail closed：只要请求带任何代理头（`cf-connecting-ip` / `x-forwarded-for` /
`cdn-loop` / `cf-ray` …）就不算本机。回归断言在 `_checks/ckTunnel.js`。

现场如果需要在手机上看汇总，用 `启动预览-带汇总口令.bat`（走 token，不是放开权限）。

写入口也顺手加了全局限流（600 条/小时）—— 开了隧道之后 `POST /api/survey` 就暴露在
公网上了，8KB 单条上限挡不住有人慢慢把磁盘写满。**限流是全局的不是按 IP 的**：
现场大部分手机走场馆 WiFi 出去，在 Cloudflare 那边共用同一个公网 IP，
按 IP 限流会把整个展位的人一起挡掉。

### 还没做的：可印刷的固定地址

快速隧道**每次重启换一个随机域名**。屏上的码是实时画的所以没问题，
但 SOP 里提到的「展位二维码」如果要印在易拉宝/立牌上，就需要一个永久地址 ——
那要用你们自己的域名做命名隧道或 Cloudflare Pages，需要 Cloudflare 账号授权。

## 人声：整句预渲染（替掉 speechSynthesis）

**「太机械化电子化」的根因**：大屏一直在用浏览器 `speechSynthesis`，
而这台机器上装的中文音色**只有一个** —— `Microsoft Huihui Desktop`，
2013 年那代 SAPI5 拼接式合成。不是参数调坏了，是引擎老了 13 年，
`rate` / `pitch` 怎么调都救不回来。

它还有两个现场层面的问题：换一台机器可能**根本没有中文音色**（播报直接静默消失），
以及**朗读时长不可控**（同一句话不同引擎能差一倍，节奏设计全废）。

### 为什么是整句，不是拼接

README 原来的待办第 1 条就写着「不要做数字拼接」，但 `_voice/stitch.js` 做的正是拼接
（把金额切成「一千」「二百」「八十美元」分别合成再接起来）。

拼接假的根因不是接缝的咔哒声（交叉淡化能压掉），而是**每个片段单独合成时都自带一个
句尾降调**，三个降调连着出现就是「报电话号码」的听感。这一层调参修不了。

而「金额连续所以不可能每句都预录」这个前提**是错的**：引擎里所有订单事件都是
时间的纯函数（`hash32(seed, salt)`），所以一场展会会播哪些金额**可以提前精确算出来**：

| 口径 | 数量 |
|---|---|
| 4 天展期订单总数 | 2,283 单 |
| 达到播报门槛（`tier>=rare`，即 ≥$110） | 916 条（平均 2.4 分钟一条） |
| **去重后不同金额** | **381 个** |
| 整句预渲染体积 | 55MB（WAV 24k/16bit），服务在 localhost，不用压 |

381 句。拼接省下来的体积毫无意义，却换来一个听感缺陷。

### 生成链

```
node   _voice/build-lines.js              → _voice/lines-manifest.json（381 句文案）
python _voice/render-lines.py --engine azure   → _voice/pack-azure/（音频 + index.json）
```

`--engine` 有四档，**授权状况完全不同，展会是公开商业场合，这条不能跳**：

| 引擎 | 能不能对外用 | 说明 |
|---|---|---|
| `azure` | ✓ | 正式选择。`zh-CN-XiaoxiaoNeural`，免费额度 50 万字符/月，381 句约 8 千字符 |
| `edge` | ✗ | 走 Edge 浏览器「朗读」接口，不是商用授权渠道。音色和 azure 是**同一批模型**，所以只用来选音色 / 内部试听 |
| `cosy` | ⚠ | 代码权重 Apache-2.0，但当前参考音是仓库自带的某个真人声音，声音人格权不在授权范围内 |
| `sapi` | ✓ | 就是现在这个 Huihui |

**当前包里是 `pack-edge`（试听版）。** 上会前必须拿 Azure key 重渲一遍：

```
set AZURE_SPEECH_KEY=<你的密钥>
set AZURE_SPEECH_REGION=eastasia
python _voice/render-lines.py --engine azure
```

运行时按 `pack-azure` → `pack-edge` → `pack-cosy` 优先级找包，所以渲完自动切过去，
不用改代码。落在非 azure 包上时 console 会 warn，`_checks/ckVoice.js` 会判红。

### 两处配套改动

- **播报口径改成一律 USD。** 原来念的是 `order.amount` + `order.currency`，也就是
  **本地币种** —— 一笔墨西哥订单会被念成「一万六千三百三十八 比索」。对中文观众
  没有任何尺度感，而且这正是复核记录第 2 条修过的那个坑的听觉版
  （本地币种把我们自己的数字夸大了 17 倍）。币种 × 金额的组合空间也让预渲染不可能。
- **演示键 `N` / `C` / `B` / `V` 的金额改成固定阶梯**（`CONFIG.DEMO_LADDERS`，四档各一组）。

  这一条是做完之后回头验才发现的，而且比想象的严重。这四个键是 BD 在台上的
  主要动作，金额**由按键决定、不由时间决定**，所以不在「按时间枚举」的集合里。
  它们原来是「区间内随机」（`usd: 320 + hash(n)*450`）—— 区间划分本身是对的
  （每个键完整落在一档之内，这条设计保留了），但随机出来的金额几乎必然
  不在预渲染集合里。实测覆盖率：

  | 键 | 档位 | 原区间 | 落在预渲染集合里的比例 |
  |---|---|---|---|
  | `N` | common | $9~$99 | — （低于播报门槛，不出声） |
  | `C` | rare | $120~$290 | 91.2% |
  | `B` | epic | $320~$770 | **35.9%** |
  | `V` | legendary | $850~$4,600 | **0.7%** |

  也就是说 BD 在台上按 `V` 键，**99% 的概率当场蹦出一句 2013 年的 Huihui**。
  改成阶梯之后每一档都有音频（`_checks/ckVoice.js` 逐档断言），
  而且连按拿到的是递增的漂亮数字，不会再抽到 $4,487 这种。

  引擎侧另外去掉了 `triggerOrder` 里的 `Math.random()`（全引擎唯一一处），
  并加了 `E.demoAmount(tier, n)` 供各方案取阶梯金额 ——
  **别再在区间里随机取数**，那等于把播报交给运气。

### 试听页

`_voice/试听-人声候选.html` —— 三条路线并排，含「提示音 + 人声」组合（这才是现场
实际听到的东西）、语速扫档、拼接 vs 整句对照。

顺带说清一件事：我试过用**基频范围 / 跳变率**客观量化「机械 vs 自然」，**量不出来**——
Huihui 是 13.3 半音 / 4.0%，四组数字互相咬在一起。原因是 Huihui 属于单元挑选式拼接，
用的是真人录音片段，基频本身是真人的；它难听在**单元接缝处的频谱突变**和
**整句韵律错**，这两样那两个指标都测不到。所以音色**只能靠耳朵定**，
客观数里只有时长有参考价值。

### 顺手修掉的一个潜伏 bug

`playTier()` 里传奇级大单的上升铺垫是 `riser(t - 0.45, …)` —— **起点在音符之前**。
AudioContext 刚建好时 `currentTime` 还不到 0.45，`when` 就是负数，
`setValueAtTime` 抛 RangeError，**整个 `playOrder` 中断，那一笔订单完全没声音**，
而屏上看不出任何异常。

以前不容易碰到：演示键的金额是区间随机，只有一部分落在 legendary。
改成阶梯之后 `B` / `V` 必然是 legendary，于是「开屏立刻按 B」会稳定触发。
已在 `riser()` 内部把起点夹到 `currentTime`（结束时刻不变，只截掉开头一点）。

### 从这轮复核里得到的一条通用规则

三个方案的实现者各自独立踩到**同一类 bug**：巨型数字里"某一位滚动到一半"的问题。
根因是滚动窗口按周期比例设定，而各位的周期差 10 倍以上。已写进 `_共享规格.md` §4.2：

> 滚动窗口必须按**时间**算（约 145~250ms），不能按周期比例算；
> 窗口占比超过 ~34% 的位（个位、十位）必须**整格吸附**，绝不逐帧插值。
> 也不要做"持续模糊旋转"的加油机效果 —— 动起来好看，但媒体拍照和录屏会定格在
> 半格状态，看起来像渲染 bug。**这块屏要用于传播，静帧质量就是交付质量。**

### 另外修正了一条我自己写错的规格

原规格要求主数字 cap height 达到屏高 30~50%。A、B、C 三个实现独立算出做不到：
爬虫累计数带 4.2 亿基线是 9~10 位数 + 2 个逗号，16:9 上几何上限就是 **10~20%**。
双十一那种大屏本身也是 11 位数、cap height 约 15~20% —— **冲击力来自宽度铺满 + 持续运动，
不是字高**。规格已改为「主数字占可用栏宽 85~92%，cap height 由此推导」。

如果现场屏幕物理尺寸偏小（例如 55 吋电视、观看距离 5 米），方案 B 提供了
`?hero=session` 开关，可切成"本场新增"口径（7 位数，字号能大将近一倍）。
**这个口径选择建议现场比一比再定**：累计 4.2 亿绝对量级更震撼但字号必然小；
本场 220 万字号大、且能看出"今天涨了这么多"，代价是开幕那一刻从 0 开始。
