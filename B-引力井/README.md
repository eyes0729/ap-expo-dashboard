> **全世界的 AI 正在往你的店里落。**

## 1. 设计意图

### 核心画面

一颗巨型地球占据屏幕中央偏右（直径约 53% 屏宽，右缘轻微出画）。两种流量方向相反，
**观众不需要看图例就能分清**：

| | 方向 | 颜色 | 形态 | 频率 |
|---|---|---|---|---|
| **AI 爬虫** | 外太空 1.6R → 店铺城市 | 冷青 `--crawl` | 细，急坠后贴球面滑行 | 13 条/秒，同屏 ≤ 40 |
| **AI 引荐订单** | 店铺城市 → 买家城市 | 暖金 `--order` | 粗，大圆弧 + 弧高 | 约 1 条/分钟，每次都是事件 |

冷青只属于机器，暖金只属于成交。这个分工一旦立住，整块屏就不需要任何图例。

### 为什么整屏是「暖金气质」而不是青绿

同一套 P1 深空石墨色板，方案 A 以 `--crawl` 主导，B 必须一眼可区分。做法是把暖金
钉在三个位置：**球缘收边**、**120 个城市芯点**、**订单弧线与事件卡金额**。
白色只做人口尘埃与文字，冷青只做爬虫 —— 全屏严格 2 色 + 1 个稀有色。

### 地球是怎么画出来的

- **Canvas 2D 自写投影，没有 Three.js / WebGL。** 规格禁 CDN（现场断网要照跑），
  且 WebGL 连跑 10 小时有 context lost 的确定性风险，恢复逻辑本身就是新 bug 源。
  内部分辨率锁 1920×1080，CSS 拉伸，不乘 `devicePixelRatio`。
- **点云全部来自 `APGeo.CITIES` 的真实经纬度**：每座城市一个暖金芯点，外围按 weight
  生成一簇白色卫星点（切平面圆盘采样，密度朝外衰减）。约 7,400 点。
  于是北美东西岸、西欧、东亚、南亚、澳洲的人口带自然浮现 —— 零贴图、零资源依赖。
- **球缘衰减是必须的**：弱透视会把靠边的点在屏幕上挤成一条亮带，不处理就是一圈发光环,
  也就是 2013–2018 免费模板的招牌皮肤。按屏幕半径降档 + 缩点，得到掠射角自然变暗。
- **背面点降到约 12% 透明度而不是剔除** —— 若隐若现才有体积感。
- **颗粒质感只叠在球体范围内**，`createPattern` 只在 init 调一次。
  （全屏后处理版本试过，就是 Shopify BFCM Globe 说的"始终不对味"。）
- **弧线退场是 noise dissolve**：沿弧线按段号喂 `hash32`，各段在不同时刻消失，
  线条崩解成碎片，而不是整体 opacity 淡出。弧线本体也带 hash 抖动，
  飞行途中就有颗粒感，不是一条塑料光带。

### 巨型数字是「里程表」

每个数位是一条 0–9–0 的字条，**只写 `transform: translate3d`，永不改 `textContent`**。
位置 = 数值的连续函数，所以单调递增、不可能倒退、不需要任何带回弹的缓动。

每一位的滚动窗口固定约 145ms（与位数无关）。但窗口占该位周期的比例随位数变化，
这一点是关键：十位的周期只有 10/46 ≈ 217ms，145ms 就占了 67% —— 观众随手拍一张，
2/3 的概率拍到十位停在两个字形中间。

**解法：占比超过 34% 的位（个位、十位）直接整格吸附**，每帧都是完整字形，
而且每帧都在变，"快"的感觉一点不丢。百位以上进位时才滚一次 145ms，其余时间纹丝不动，
高位始终可读；高位再加 40ms stagger，进位时形成一次自下而上的级联。

> **曾经用「速度驱动运动模糊」解这个问题，已移除。** 思路是对的（按本帧位移像素给
> 模糊半径 = 真实相机的速度 × 曝光），但在这个量级下不成立：个位每帧位移 0.77 格，
> 0.77 × 162px × 0.42 = 52px，被截到 17px 上限并把不透明度压到 50%，
> 结果在静帧里就是**两个灰色矩形块** —— 读作「缺字形 / 纹理没加载」，比它要解决的
> 半字形问题更糟。而且配角的页面数（每秒只涨 1.2）也被误判成高速位一起糊掉了。
> 这块屏要用于媒体拍照和录屏，静帧质量就是交付质量。已用 Playwright 截图复核。

### 稀有度分级

`epic` / `legendary` 才触发：地球呼吸缩放 ≤ 1.5%（sin 半周期，无回弹）、
屏幕暗角短暂加深、主数字背后一处体积光 ≤ 8%、卡片更高更亮、订单弧线停留更久。
`common` / `rare` 只有声音与卡片滑入。**全篇没有弹跳缩放，也没有发光呼吸。**

## 5. 已知取舍

### 5.1 主数字 cap height 是屏高 11%，不是 35%（最重要的一条）

这是算术上的硬约束，不是偷懒。下面的数字全部是浏览器里实测出来的
（Bahnschrift 存在时 `0` 的字宽 = 0.549em，`,` = 0.228em）：

- 引擎实测 `metrics.crawls` 起点是 **4.20 亿**，也就是 **9 位数 + 2 个逗号**。
  （我第一版按 7 位做，会直接砍掉最高位 —— 数字是错的。这是必须按 9 位排的原因。）
- 9 × 0.549 + 2 × 0.228 = **5.40em**。左栏可用宽度 880px（再往右就压到球体左缘 x≈997）。
- → 实测字号 **162px**，字格 211px，槽宽 89px，整块 875px，左缘正好落在 116px 边距上。
- → cap height ≈ **115px = 屏高 10.6%**。
- 要做到 cap 378px（35% 屏高）需要字号 532px，整块 **约 2,900px 宽** ——
  一块 1920 宽的屏放不下，跟版面无关，是位数决定的。

如果老板坚持要更大，只有三条路，都需要他先拍板：

1. **数字压到球体上**：右缘放到 x≈1130，字号可到 **188px**（cap 133px / 12.3%，+16%）。
   代价是暖金球缘那条 1.5px 的线会横穿最后一位，看起来像失误。收益也不大。
2. **换主角**：用 `metrics.pages`（7 位，614 万）当主数字，字号可到 **204px**
   （cap 145px / 13.4%）。代价是「AI 爬虫访问量」这个最有冲击力的叙事降级成配角。
3. **改口径**：让产品同意主数字显示「本场 AI 爬虫访问」而不是历史累计
   （约 200~370 万，7 位，字号同样可到 204px）。这是我个人最推荐的一条 ——
   数字更小但更可信，而且「今天就有 300 万次」比「历史累计 4.2 亿」对商家更有说服力，
   顺带还解决了「累计数字涨到 10 位、版面得重排」的问题。
   **共享引擎现在已经提供 `metrics.session.crawls`，所以这条改动是一行代码**：
   `app.js` 的 `frame()` 里把 `m.crawls` 换成 `m.session.crawls` 即可，
   字号与字宽槽会自动按新位数重算（见下）。

> **注意（跨方案协作）**：`_shared/engine.js` 在我开发期间被另一个会话改过两次
> （加了 `CRAWLS0` / `ORDERS0` / `GMV0` 基线，以及 `metrics.session.*` 本场增量）。
> 因此我**没有把数位数写死**：`MAIN_DIGITS` / `PAGE_DIGITS` 在启动时按引擎的真实量级
> 算出来，运行期涨位也会自动重排（`ensureDigits()`）。
> 如果之后又有人调 `CRAWLS0` 的量级，这块屏不需要改代码 —— 但**字号会随位数变化**，
> 位数每多一位，主数字约小 10%。上会前请确认量级已经定稿。

### 5.2 事件卡改成「常驻最近 2 单」，不是「到时消失」

规格原意是卡片停留几秒后退场。但订单约 1 分钟一单、卡片只停 8 秒 —— 左下角会有
**85% 的时间是「一个标题加一片空白」**，大屏上这是硬伤。改成常驻 2 张（新单从顶部滑入、
把旧单顶出视野），旧的那张压到 60% 亮度。事件感来自「声音 + 信使流星 + 滑入」，
不来自「消失」。事件区因此占屏高 16%，仍在规格的 15~20% 区间内。

启动时会用引擎自己的生成器补两单（common + epic 各一），保证首帧事件区就是满的。

### 5.3 爬虫展示速率 22/s，高于规格建议的 2~4/s（复核后由 13/s 上调）

真实速率 42/s。试过 6.5/s：球面上只有三五条孤线，读作「几根杂线」而不是「一场雨」。
复核截图显示 13/s 时同屏只有 4~6 条可见（弧线只画尾部 46% 的长度，看着像几条短划），
所以又把展示速率提到 22/s、尾巴加长到 66%。现在同屏稳定 30~40 条，仍在规格上限内，
仍是 2 倍降采样。

### 5.4 个位、十位读不到精确值

这两位每帧整格跳变（每秒分别跳 46 次和 4.6 次），肉眼读不到具体数字，只能读到
「它在飞快地变」—— 而这正是要传达的信息。**每一帧都是完整字形**，所以截图和录屏
都干净，这跟"读不出数字"是两件事。若有人坚持要求个位可读，唯一解法是把显示值
取整到十位并在旁边标注（方案 C 就是这么做的，标了 `ROUNDED TO 10`）。

### 5.5 超宽屏留黑边

21:9 / 32:9 上是等比缩放 + 左右留黑，没有做弹性切栏。规格允许，但如果现场是 32:9
的拼接屏，值得再花半天做一个 3 栏版式。

### 5.6 公开数据没有上屏

Adobe 的 66% / 1.42×、Shopify 的 13× 都没放。原因有两个：全屏文案总量要守住 25 汉字；
以及真数据给假数字背书这件事，视觉分区做不好就是负分。如果 BD 需要论据，
建议做成一张单独的静态展板放在屏幕旁边，而不是塞进这块屏。

### 5.7 `will-change` 一次都没用

规格允许「只在动画期间加」。这里全部动画都是 `translate3d` / `opacity` / `filter`，
本身就会提升合成层，加 `will-change` 只会额外占纹理，所以干脆不用。

## 6. 上会前待办

1. **人声必须换成预先离线合成的音频文件。** 现在靠浏览器 `speechSynthesis` 顶着，
   展会机上可能没有中文音色、或依赖联网。用 Azure / ElevenLabs 免费额度一次性生成
   整句（金额可以做成「数字片段 + 固定句尾」拼接），落成本地 mp3/ogg。
   —— 这一条不做，现场大概率是**哑的**。
2. **在真机上量一次真实帧率**：接好 LED、开全屏、跑 30 分钟，看 `window.APDiag.fpsAvg`。
   低于 40 时 console 会打警告（已实现），但**自动软重置没做**，正式版需要补。
3. **确认 `CONFIG.PAGES0` 与 crawls 量级的对外口径**。现在是 614 万页 / 4.20 亿次抓取。
   规格写了「不得超过公司对外最大公开口径 × 1.2」，需要产品签一次字。
4. **主数字尺寸决策**（见 5.1）—— 需要老板在三条路里选一条，或者接受 11%。
5. **音频开机自检**：现场接 HDMI 会把默认输出切到显示器。启动遮罩点击时已经会自动跑
   `APAudio.selfTest()`（两声铃），听不到就是走错了输出设备。
6. **店铺名碰撞复查**：引擎的虚构品牌名已避开知名 DTC 品牌，但上会前值得再搜一遍。
7. 现场备一台笔记本 + 一根 HDMI，`R` 键可以在任何时候把画面拉回干净状态。
8. 彩排时用 `1` / `3` 键调速率跑一遍全流程，确认 `B` 键的大单在讲解节奏上能踩准。

## 主 agent 复核后的改动（2026-08-18）

用 Playwright 在 1920×1080 真跑截图复核后改了六处。与上文冲突的地方**以本节和代码为准**。

1. **移除速度驱动运动模糊，改为整格吸附**（`Odometer.prototype.update`）。
   理由见上文第 2 节的引用块 —— 静帧读作灰色色块，且配角页面数被误糊。
2. **地球提亮加密**（`globe.js`）。原来在截图里是一个近乎全黑的炭灰色圆 + 几簇很淡的
   白点，**看不出是地球**，而这是本方案的全部卖点。改动：
   点云分档 alpha 整体提亮（档 0 由 0.40 → 0.62，背面档同步提亮）、
   点径 `BSIZE` 由 `[1,2,3,3,4,4]` → `[2,3,4,4,5,5]`、
   透视缩放由 `P.k*0.80` → `P.k*0.95`、点径上限 4 → 6、
   每城市卫星点数由 `16+w*9` → `22+w*13`（总点数约 5,000 → 7,400）、
   经纬线正面 opacity `.055` → `.090`、背面 `.018` → `.026`。
3. **爬虫弧线密度**：展示速率 `pollCrawls(13)` → `pollCrawls(22)`，
   飞行时长 1.22~1.77s → 1.45~2.15s，尾巴 `tail` 0.46 → 0.66
   （原来只画 46% 弧长，同屏看着像几条零散短划，读不出"一场雨"）。
   同屏稳定 30~40 条，仍在规格上限内。
4. **补换算行**（`.conv`）：`≈ 每 57 秒一笔 AI 引荐订单 / ≈ 每分钟 54 个新 AP 页面`。
   既填掉平台占比条与订单区之间约 80px 的死空间，也解决"巨型数字没有参照系"的问题。
   注意这一栏是绝对定位布局，`.conv` 也必须绝对定位（top:704px）。
5. **新增 `?hero=session` 开关**：主数字切成 `metrics().session.crawls`（本场新增，
   7 位数，字号可以大将近一倍），标签同步改成「本场 AI 爬虫访问 · THIS SHOW」。
   默认仍是累计口径。两种口径的取舍：累计数字绝对量级更震撼但位数多、字号必然小；
   本场口径字号大、能看出"今天涨了这么多"，代价是开幕那一刻从 0 开始。
   **现场比一比再定，所以做成开关而不是替换。**
6. **合规角标提亮**：`#badge` opacity `.52` → `.78`。原来叠在地球上几乎读不到，
   而规格要求它在任何一帧截图里都必须可辨。

关于上文「主数字 cap height 只有 10.6%」的分析：算术是对的，但**结论要改** ——
共享规格里"cap height 达屏高 30~50%"这条要求本身写错了，已修订为
「主数字占可用栏宽 85~92%，cap height 由此推导」。双十一那种大屏本身也是 11 位数、
cap height 约 15~20%，冲击力来自**宽度铺满 + 持续运动**，不是字高。本方案不需要为此改设计。

另外这三处共享引擎的改动本方案直接受益，不需要自己实现：
`fmtMoney` 一律 en-US 排版（防 CAD/AUD/SGD/MXN 的裸 `$` 被误读成美元）、
店铺身份空间改成单射的 464 个（店名确定则国家/货币/城市也确定）、
`metrics().gmv` 含历史基线并与 `orders` 同口径。
